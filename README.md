# Сессионные рекомендации на данных Coveo

Проект рекомендательной системы для интернет-магазина: по просмотрам и поиску в анонимной сессии подобрать товары, которые пользователь может купить до её завершения.

Реализованы подготовка Coveo по `observed_purchases_v1`, исторический пакет, точный отбор кандидатов, признаки, обучение и локальная оценка. Первая модель Coveo обучена и проверена; принят отчёт C_smoke на 50 000 сессий. Сервис не реализован. Полнота телеметрии остаётся неизвестной.

## Задача и данные

Алгоритм отбирает до 300 кандидатов и возвращает до 20 различных допустимых товаров. Обучение использует последующие зарегистрированные покупки той же сессии; будущие события не должны попадать в признаки.

Источник — Coveo SIGIR eCom Data Challenge: `browsing_train.csv`, `search_train.csv`, `sku_to_content.csv`. Исходные данные не включены в репозиторий.

Первый вариант — GCS+Rk: граф связей товаров, раздельные сходства описаний и изображений, поисковый контекст и ранжировщик на LightGBM с собственными производными. Нейросеть, ANN и реальный A/B — последующие этапы.

## Что работает

- Неизменяемые типы префикса, отдельные цели и веса, строгая сериализация UTF-8 и int64.
- Устойчивые численные функции, нормировка векторов, проверяемая арифметика времени, агрегация последней группы.
- Локальные артефакты с хешами и зависимостями; Parquet и числовые матрицы без `pickle`.
- Схемы паспорта и признаков, реестр 30 нормативных проверок и EXPL01.
- Проверка допуска по паспорту 2.10 с протоколом `observed_purchases_v1` и результатам этапов. Проверки кода запускаются через `pytest` и не заменяют допуск фактического запуска.
- Порционное чтение CSV, внешняя сортировка и канонизация полных блоков с происхождением и кратностями.
- Видимые префиксы по двум временам, корзина, поисковый контекст и расписание запросов.
- Семь периодов, воспроизводимый отбор целых сессий после допуска и отдельные зарегистрированные цели. Пустая цель не считается отрицательным исходом; покупочная когорта не рассчитывается.
- Статическая проверка `sealed_block_v1`; общие таблицы подготовки, проверка хешей и повтор без перезаписи результатов.
- Отдельная потоковая проверка трёх исходных CSV Coveo: схема, время, векторы, размеры и SHA-256 без подготовки сессий, целей и показателей покупок.
- Исторический пакет по полным сессиям A_G: разрежённый граф, сессионные счётчики, популярность, модальности и словарь категорий. Публикация и загрузка проверяют состав, формы и зависимости частей.
- Восемь источников кандидатов, точные квоты и объединение происхождений, заполнение популярностью, отдельный резерв. Уже купленные товары исключаются.
- Общий `FeatureEngine` и [схема 93 столбцов](/configs/feature_schema.json): численные значения, маски и категория. Пакетная команда сохраняет три общие таблицы, без целей и обучающих весов.
- Обучающие группы из готовых таблиц B, собственные производные `session_lambdas_v1`, LightGBM 4.6.0 по закреплённому рецепту. Сохранение и загрузка модели, основная выдача до 20 SKU по сырым баллам; резерв не ранжируется моделью.
- Локальные GCS+Rk/P/R, отдельные таблицы ответов и оценок, Hit@20, разложение потерь, диагностика источников и кратностей, календарные интервалы и отчёт без повторного обучения.

Условия стадий паспорта проверяются отдельно от исполнения тестов; локальная оценка не требует готового сервиса. На реальном B из 50 000 сессий завершены допуск Э1-10, расчёт признаков и обучение Э4-08. C_smoke прошёл `post_training/evaluate`; [результаты и ограничения](/README.md#c_smoke-и-оценка-э5) приведены ниже.

## Запуск Э0

Нужны Python 3.11.9 и uv 0.10.4. Из корня проекта:

```sh
uv sync --locked
uv run --no-sync coveo-recsys environment
uv run --no-sync ruff format --check .
uv run --no-sync ruff check .
uv run --no-sync mypy
uv run --no-sync pytest -m "not coveo and not load"
```

Версии и хеши закреплены в [uv.lock](/uv.lock), состав зависимостей — в [pyproject.toml](/pyproject.toml). Базовая установка не включает PyTorch и не требует GPU; необязательный CPU-профиль устанавливается через `uv sync --locked --extra neural`.

Создание и проверка паспорта:

```sh
uv run --no-sync coveo-recsys manifest init --run-id e0 --run-dir runs/e0
uv run --no-sync coveo-recsys manifest validate --manifest runs/e0/manifest.json --run-dir runs/e0 --stage preflight
```

Последняя команда должна отказать в допуске: у проекта паспорта нет фактических данных и полного набора обязательных результатов. Успех проверок кода не означает успешный `preflight`.

Паспорт сохраняется в `runs/e0/manifest.json`, вне Git; повтор `manifest init` его не перезаписывает. После изменения закреплённых кода, входов или настроек нужен новый запуск. Команды `serve` и остальные будущие этапы возвращают явный отказ.

Используется один паспорт, результаты стадий хранятся отдельно. До открытия соответствующих оценочных данных фиксируется план; при проверке его закреплённый хеш передаётся через `--plan-reference NAME=SHA256`. Неподтверждённые флаги успеха не дают допуска. Прежние форматы паспорта не поддерживаются.

## Подготовка данных Э1

Пример использует только [искусственные CSV](/tests/fixtures/e1/), [профиль](/configs/synthetic_csv.json) и [план](/configs/synthetic_preparation.json). Это не описание реального формата поставки Coveo.

```sh
uv run --no-sync coveo-recsys data inspect --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --run-id e1 --run-dir runs/e1
uv run --no-sync coveo-recsys data prepare --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --plan configs/synthetic_preparation.json --run-id e1 --run-dir runs/e1
```

Ожидается: из 3 рассмотренных сессий выбраны `s1` и `s2`, сохранены 8 канонических блоков и 2 запроса; `s3` исключена из-за покупки в первом блоке. Цель `s1` содержит `B`, цель `s2` пуста со статусом `unknown`. Итог — `runs/e1/reports/preparation.json` и общие таблицы событий, сессий, запросов и целей. Посессионных файлов и журнала шагов нет.

Повтор `data prepare` проверяет входы, код, план и контрольные суммы готовых таблиц. Незавершённый общий проход пересчитывается; уже опубликованные файлы должны совпасть, перезапись запрещена. Для порционного чтения целых сессий предусмотрен [DatasetAccess](/src/coveo_recsys/data/access.py): A_N и закрытые периоды не открываются через этот интерфейс, цели нельзя прочитать как префиксы.

Контракты подготовки имеют версию 3; события и остальные неизменённые записи — версию 2. Формат общих таблиц — `preparation_tables_v1`. Прежние посессионные результаты переносятся однократно с проверкой равенства записей; рабочие читатели старый формат не поддерживают. Поддерживается историческое `a=t`; полнота опубликованных строк проверяется отдельно от неизвестной полноты телеметрии. Защита рабочей СУБД и квитанции остаются Э6.

## Проверка поставки Coveo

Исходные CSV размещаются в `data/01_raw/` и не входят в Git. Для полученной поставки используется [проверенный профиль](/configs/coveo_supply_v1.json):

```sh
uv run --no-sync coveo-recsys data inspect-supply --input-dir data/01_raw --profile configs/coveo_supply_v1.json --run-id coveo-supply --run-dir runs/coveo-supply
```

Команда читает все три файла, сверяет их размер и SHA-256, затем повторно хеширует входы перед публикацией. Сохраняет только структурную сводку и журнал ресурсов; строки, идентификаторы и векторы не выводит. При прерывании или повреждении незавершённого артефакта используйте новый `run-id` и каталог запуска, не перезаписывая прежний.

Формат трёх CSV подтверждён; покрытие телеметрии неизвестно. Проверка поставки не создаёт цели и не даёт допуска `preflight`.

### Подготовка реальных сессий

Адаптер использует те же канонизацию, расписание и расчёт целей, что и искусственный пример.
[План Coveo](/configs/coveo_preparation.json) закрепляет семь периодов, seed 17,
до 50 000 допущенных сессий A_G и пределы: 4 часа, 8 ГиБ памяти, 4 ГиБ временных файлов.
Если допущенных сессий меньше, сохраняются все; пустой набор не пригоден для Э2.

```sh
uv run --no-sync coveo-recsys data prepare --input-dir data/01_raw --profile configs/coveo_supply_v1.json --plan configs/coveo_preparation.json --run-id coveo-ag50000-new --run-dir runs/coveo-ag50000-new
```

Краткие сведения из обоих CSV сводятся во временной SQLite-таблице. После проверки
первого запроса и календарного допуска выбираются минимальные хеши ID. Затем
читаются все строки выбранных сессий, включая хвосты; число строк и происхождение
сверяются с отбором. Наличие цели не влияет на выбор. Даты и размер закрепляются
заранее. Полные проходы CSV и проверка хешей нужны даже для малого A_G.

Первые запросы и цели сохраняются раздельно в `datasets/A_G/prefixes.parquet`
и `datasets/A_G/targets.parquet`, события — в `canonical/A_G.parquet`,
реестр сессий — в `preparation/sessions.parquet`. Выбранные ID, причины исключений,
параметры и контрольные суммы таблиц входят в `reports/preparation.json`.
Цель содержит все различные зарегистрированные покупки в установленном окне.
Пустая цель имеет статус `unknown`. Ни конец CSV, ни покупка, ни её отсутствие
не подтверждают полноту телеметрии. Для B используется отдельный план с ненулевым
объёмом только этого периода; A_N/C_smoke/C_select/E/D остаются закрытыми.

`reports/preparation.json` публикуется последним, со статусом `completed`, после
проверки входов и таблиц. Незавершённый набор не допускается к исторической сборке.
Возобновление не продолжает чтение с произвольной строки CSV. После изменения
кода или плана нужен новый каталог запуска. Для уже перенесённых 50 000 сессий
повторять подготовку из CSV не требуется.

Сводка `composition` считает товарные действия по каноническим событиям всех
выбранных сессий, без исходных повторов `set_v1`; число исходных строк сохранено
отдельно. Покупки полного журнала отделены от покупок целевого окна. Повторяемость
SKU измеряется между сессиями и по разным блокам внутри сессии, не по кратности строк.
Временный диск проверяется во время чтения и сортировки; общий размер результата —
на границах стадий и при завершении, не как непрерывный пик.

## Исторический пакет Э2

Для готового A_G используется [конфигурация сборки](/configs/coveo_historical.json).
Она закрепляет путь подготовки и хеш её итоговой сводки, параметры и
пределы ресурсов. В новом окружении сначала нужна собственная подготовка;
её хеши нельзя заменять хешами чужого запуска.

```sh
uv run --no-sync coveo-recsys historical build --config configs/coveo_historical.json --run-id coveo-historical-ag50000-v1 --run-dir runs/coveo-historical-ag50000-v1
```

Готовый состав — `historical/package.json`; таблицы, массивы и отчёт сборки лежат
рядом в каталоге запуска. Сырые CSV поведения и поиска повторно не готовятся.
Код сборщика может отличаться от закреплённого кода подготовки.

Повтор проверяет входы и готовый пакет. При прерывании между опубликованными
частями вычисления повторяются, совместимые файлы не перезаписываются.
Восстановление с произвольной строки или ребра не поддерживается.
После изменения кода сборщика или его настроек нужен новый каталог запуска.

## Кандидаты и признаки Э3

Малый воспроизводимый путь без реальных данных:

```sh
uv run --no-sync pytest tests/integration/test_e3_pipeline.py tests/integration/test_e3_context.py tests/integration/test_e3_integrity.py -q
```

Проверки создают тестовую подготовку и исторический пакет, запускают `features build`,
сравнивают пакетный результат с последовательным и проверяют прерывание, повтор
и несовместимые входы. Для своей тестовой подготовки команда принимает
[настройки запуска](/configs/README.md#настройки-признаков-э3):

```sh
uv run --no-sync coveo-recsys features build --config runs/e3/features.json --run-dir runs/e3/result --run-id e3 --period B
```

Результат — `features/candidates.parquet`, `features/fallback.parquet`,
`features/values.parquet` и итоговая сводка `reports/features.json` внутри каталога
запуска. Резерв не объединяется с основным набором и не проходит ранжировщик.
При изменении кода, схемы или входов нужен новый каталог результата.

Реальный B требует отдельного допуска Э1-10 до чтения таблиц. Обе команды —
`features build` и `train ranker` — проверяют паспорт и его привязку к фактическим
входам, коду и настройкам. Готовый A_G повторно подготавливать не требуется.

## Обучение и применение Э4

Проверка полного пути на искусственном наборе с обучающими парами:

```sh
uv run --no-sync pytest tests/integration/test_e4_pipeline.py -q
```

Для подготовленных входов используются [настройки обучения](/configs/README.md#настройки-обучения-э4):

```sh
uv run --no-sync coveo-recsys train ranker --config runs/e4/training.json --run-dir runs/e4/result --run-id e4
```

Команда соединяет сохранённые основные кандидаты и признаки с отдельными целями B.
Пустые цели остаются неизвестными, покупки вне кандидатов не добавляются.
Отсутствие пар во всём наборе возвращает `insufficient` и ненулевой код, без модели.
Перед выделением матрицы проверяются верхняя граница числа строк и ресурсы.

Результат — `models/ranker.txt` в штатном формате LightGBM и `reports/ranker.json`
с входами, рецептом, фактическими деревьями, размерами листьев и расходом ресурсов.
Сводка публикуется после проверки сохранённой модели. Прерванное обучение можно
повторить целиком с теми же входами; несовместимые результаты не перезаписываются.
[Загрузчик](/src/coveo_recsys/ranking/load.py) и [применение](/src/coveo_recsys/ranking/predict.py)
не читают цели и обучающие таблицы. Баллы — не вероятности покупки.

## Локальная оценка Э5

Для закреплённых входов и [настроек оценки](/configs/README.md#настройки-оценки-э5):

```sh
uv run --no-sync coveo-recsys replay --period C_smoke --config runs/e5/replay.json --run-dir runs/e5/result --run-id e5
uv run --no-sync coveo-recsys report --run runs/e5/result
```

Команды не создают настройки или допуск автоматически. `replay` использует готовую модель и один набор сессий для GCS+Rk, популярности A_G (P) и последних просмотров с заполнением популярностью (R). Цели присоединяются после сохранения ответов. Неизвестная цель не становится промахом; целевая сессия с пустой выдачей остаётся в знаменателе.

Результат — две общие таблицы `replay/answers.parquet`, `replay/sessions.parquet` и `reports/replay.json`/`replay.md`. `report` проверяет таблицы и формирует Markdown из готовой сводки, не читая сырьё и не применяя модель. Незавершённый расчёт повторяется целиком; прежние готовые результаты не перезаписываются.

Режим — `ideal_deterministic`, не воспроизведение рабочего сервиса. Необоснованные или недостаточные интервалы сохраняют причины. До D остаётся `S_offline=not_run`, бизнес-эффект — `not_observed`.

## Проверки и ограничения

Последний полный локальный прогон: 1524 теста пройдены, 7 проверок символических
ссылок пропущены из-за ограничений Windows. Mypy, `ruff check .` и
`ruff format --check .` прошли. Остаётся предупреждение об устаревшем API в
зависимости Starlette. Wheel собран и установлен обычным способом в отдельное
окружение: 61 проверка прошла, включая сводки, записи диагностики, замер памяти и путь от CSV
через подготовку, исторический пакет, признаки и обучение до отчёта. Это проверки
кода на малых примерах, не измерение качества Coveo.

[GitHub Actions](/.github/workflows/checks.yml) при `push` и `pull_request` проверяет проект на Ubuntu: обычную установку пакета (`--no-editable`), форматирование и правила Ruff, типы, тесты без меток `coveo` и `load`, сборку и запуск консольной команды. Удалённый запуск ещё не проверен.

Текущий A_G — 50 000 сессий в `runs/coveo-ag50000-compact-v1/`, вне Git.
Рассчитанные данные перенесены в четыре общие таблицы без изменения записей.
Отбор сохранён: из 5 010 682 рассмотренных сессий 655 365 имеют первый подходящий
запрос, 612 700 проходят календарный допуск; ID выбраны по хешу, без предпочтения
сессий с покупками.

| Состав A_G | Прежние 10 000 сессий | Текущие 50 000 сессий |
|---|---:|---:|
| Исходные строки поведения / поиска | 107 158 / 1 642 | 528 951 / 8 510 |
| Канонические блоки | 77 386 | 382 338 |
| Первые запросы | 10 000 | 50 000 |
| Товарные SKU | 7 264 | 14 314 |
| События `detail` | 31 214 | 154 018 |
| События `purchase` | 188 | 1 053 |
| Сессии с зарегистрированной целью | 137 | 693 |
| Пары `(сессия, SKU)` с просмотрами в разных блоках | 5 451 | 26 762 |

У 49 307 сессий текущего набора цель пуста и имеет статус `unknown`.
Полнота телеметрии неизвестна для всех сессий. События `purchase` не равны числу

Числа в спецификации — требования и расчётные примеры.

Основная метрика — Hit@20: доля сессий с зарегистрированной будущей покупкой, в которых первая выдача содержит хотя бы один целевой SKU. Цель включает все различные SKU зарегистрированных покупок после первого запроса в установленном окне той же сессии. Метрика не измеряет прирост покупок от рекомендаций; для такого вывода нужен эксперимент с показами.
