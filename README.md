# Сессионные рекомендации на данных Coveo

Проект рекомендательной системы для интернет-магазина: по просмотрам и поиску в анонимной сессии подобрать товары, которые пользователь может купить до её завершения.

Реализованы подготовка Coveo по `observed_purchases_v1` и сборка исторического пакета: каталог, три графовых отношения, статистики и метаданные. Рекомендации пока не выдаются: отбор кандидатов, обучение и сервис ещё не реализованы. Полнота телеметрии остаётся неизвестной.

## Задача и данные

Планируемая система отбирает до 300 кандидатов и возвращает до 20 различных допустимых товаров. Обучение использует последующие покупки той же сессии; будущие события не должны попадать в признаки.

Источник — Coveo SIGIR eCom Data Challenge: `browsing_train.csv`, `search_train.csv`, `sku_to_content.csv`. Исходные данные не включены в репозиторий.

Первый вариант — GCS+Rk: граф связей товаров, раздельные сходства описаний и изображений, поисковый контекст и ранжировщик на LightGBM с собственными производными. Нейросеть, ANN и реальный A/B — последующие этапы.

## Что работает

- Неизменяемые типы префикса, отдельные цели и веса, строгая сериализация UTF-8 и int64.
- Устойчивые численные функции, нормировка векторов, проверяемая арифметика времени, агрегация последней группы.
- Локальные артефакты с хешами и зависимостями; Parquet и числовые матрицы без `pickle`.
- Схемы паспорта и признаков, реестр 30 нормативных проверок и EXPL01.
- Проверка допуска по паспорту 2.10 с протоколом `observed_purchases_v1` и результатам этапов. Проверки кода запускаются через `pytest` и не заменяют допуск фактического запуска.
- Порционное чтение CSV, внешняя сортировка и канонизация полных блоков с происхождением и кратностями.
- Видимые префиксы по двум временам, корзина, поисковый контекст и расписание запросов.
- Семь периодов, воспроизводимый отбор целых сессий после допуска и отдельные зарегистрированные цели. Пустая цель не считается отрицательным исходом; покупочная когорта не рассчитывается.
- Статическая проверка `sealed_block_v1`; сохранение и возобновление подготовки с проверкой хешей.
- Проверка общих зависимостей один раз за операцию и свежий заключительный обход перед успехом.
- Отдельная потоковая проверка трёх исходных CSV Coveo: схема, время, векторы, размеры и SHA-256 без подготовки сессий, целей и показателей покупок.
- Исторический пакет по полным сессиям A_G: разрежённый граф, сессионные счётчики, популярность, модальности и словарь категорий. Публикация и загрузка проверяют состав, формы и зависимости частей.

Условия стадий паспорта проверяются отдельно от исполнения тестов; локальная оценка не требует готового сервиса. Искусственные отчёты отделены от результатов на Coveo. Точные столбцы признаков остаются Э3, функция производных ранжировщика — Э4.

## Запуск Э0

Нужны Python 3.11.9 и uv 0.10.4. Из корня проекта:

```sh
uv sync --locked
uv run --no-sync coveo-recsys environment
uv run --no-sync ruff format --check .
uv run --no-sync ruff check .
uv run --no-sync mypy
uv run --no-sync pytest -m "not coveo and not load"
```

Версии и хеши закреплены в [uv.lock](/uv.lock), состав зависимостей — в [pyproject.toml](/pyproject.toml). Базовая установка не включает PyTorch и не требует GPU; необязательный CPU-профиль устанавливается через `uv sync --locked --extra neural`.

Создание и проверка паспорта:

```sh
uv run --no-sync coveo-recsys manifest init --run-id e0 --run-dir runs/e0
uv run --no-sync coveo-recsys manifest validate --manifest runs/e0/manifest.json --run-dir runs/e0 --stage preflight
```

Последняя команда должна отказать в допуске: у проекта паспорта нет фактических данных и полного набора обязательных результатов. Успех проверок кода не означает успешный `preflight`.

Паспорт сохраняется в `runs/e0/manifest.json`, вне Git; повтор `manifest init` его не перезаписывает. После изменения закреплённых кода, входов или настроек нужен новый запуск. Команды `train`, `serve` и остальные будущие этапы возвращают явный отказ.

Используется один паспорт, результаты стадий хранятся отдельно. До открытия соответствующих оценочных данных фиксируется план; при проверке его закреплённый хеш передаётся через `--plan-reference NAME=SHA256`. Неподтверждённые флаги успеха не дают допуска. Прежние форматы паспорта не поддерживаются.

## Подготовка данных Э1

Пример использует только [искусственные CSV](/tests/fixtures/e1/), [профиль](/configs/synthetic_csv.json) и [план](/configs/synthetic_preparation.json). Это не описание реального формата поставки Coveo.

```sh
uv run --no-sync coveo-recsys data inspect --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --run-id e1 --run-dir runs/e1
uv run --no-sync coveo-recsys data prepare --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --plan configs/synthetic_preparation.json --run-id e1 --run-dir runs/e1
```

Ожидается: из 3 рассмотренных сессий выбраны `s1` и `s2`, сохранены 8 канонических блоков и 2 запроса; `s3` исключена из-за покупки в первом блоке. Цель `s1` содержит `B`, цель `s2` пуста со статусом `unknown`. Итог — `runs/e1/reports/preparation.json`, отдельные таблицы — в `datasets/`, журнал — в `preparation/progress/`.

Повтор `data prepare` с теми же входами проверяет сохранённые зависимости. После прерывания используется совместимый канонический индекс; завершённые файлы не перезаписываются. Изменённые входы, код, план или повреждённые файлы дают отказ. Для чтения подготовленных наборов предусмотрен [DatasetAccess](/src/coveo_recsys/data/access.py): A_N и закрытые периоды не открываются прямым путём через этот интерфейс, цели нельзя прочитать как префиксы.

Изменённые контракты подготовки имеют версию 3; события и остальные неизменённые записи — версию 2. Прежние результаты подготовки нужно перестроить. Поддерживается историческое `a=t`; полнота чтения опубликованных строк проверяется отдельно от неизвестной полноты телеметрии. Защита рабочей СУБД и квитанции остаются Э6. Кеш проверенных зависимостей действует только внутри одной команды.

## Проверка поставки Coveo

Исходные CSV размещаются в `data/01_raw/` и не входят в Git. Для полученной поставки используется [проверенный профиль](/configs/coveo_supply_v1.json):

```sh
uv run --no-sync coveo-recsys data inspect-supply --input-dir data/01_raw --profile configs/coveo_supply_v1.json --run-id coveo-supply --run-dir runs/coveo-supply
```

Команда читает все три файла, сверяет их размер и SHA-256, затем повторно хеширует входы перед публикацией. Сохраняет только структурную сводку и журнал ресурсов; строки, идентификаторы и векторы не выводит. При прерывании или повреждении незавершённого артефакта используйте новый `run-id` и каталог запуска, не перезаписывая прежний.

Формат трёх CSV подтверждён; покрытие телеметрии неизвестно. Проверка поставки не создаёт цели и не даёт допуска `preflight`.

### Подготовка реальных сессий

Адаптер использует те же канонизацию, расписание и расчёт целей, что и искусственный пример.
[План Coveo](/configs/coveo_preparation.json) закрепляет семь периодов, seed 17,
до 10 000 допущенных сессий A_G и пределы: 2 часа, 1 ГиБ памяти, 2 ГиБ временных файлов.
Если допущенных сессий меньше, сохраняются все; пустой набор не пригоден для Э2.

```sh
uv run --no-sync coveo-recsys data prepare --input-dir data/01_raw --profile configs/coveo_supply_v1.json --plan configs/coveo_preparation.json --run-id coveo-ag10000-observed-v1 --run-dir runs/coveo-ag10000-observed-v1
```

Краткие сведения из обоих CSV сводятся во временной SQLite-таблице. После проверки
первого запроса и календарного допуска выбираются минимальные хеши ID. Затем
читаются все строки выбранных сессий, включая хвосты; число строк и происхождение
сверяются с отбором. Наличие цели не влияет на выбор. Даты и размер закрепляются
заранее. Полные проходы CSV и проверка хешей нужны даже для малого A_G.

Первые запросы и цели сохраняются раздельно в `datasets/A_G/`, канонические блоки —
в `canonical/`, выбранные ID и причины исключений — в `preparation/selection.json`.
Цель содержит все различные зарегистрированные покупки в установленном окне.
Пустая цель имеет статус `unknown`. Ни конец CSV, ни покупка, ни её отсутствие
не подтверждают полноту телеметрии. Другие реальные периоды пока не готовятся.

`reports/preparation.json` со статусом `materialized` означает запись таблиц,
но не завершение команды. Итоговая проверка отмечается как `completed` в
`preparation/executions/`; там же — ресурсы, чтения и неудачные попытки.
Повтор сверяет исходники и переиспользует готовые стадии. Незавершённый отбор или
сортировка начинается заново, продолжения с последней строки CSV нет. После изменения кода
или плана нужен новый каталог запуска.

Сводка `composition` считает товарные действия по каноническим событиям всех
выбранных сессий, без исходных повторов `set_v1`; число исходных строк сохранено
отдельно. Покупки полного журнала отделены от покупок целевого окна. Повторяемость
SKU измеряется между сессиями и по разным блокам внутри сессии, не по кратности строк.
Временный диск проверяется во время чтения и сортировки; общий размер результата —
на границах стадий и при завершении, не как непрерывный пик.

## Исторический пакет Э2

Для готового A_G используется [конфигурация сборки](/configs/coveo_historical.json).
Она закрепляет конкретную подготовку и её завершённое выполнение, параметры и
пределы ресурсов. В новом окружении сначала нужна собственная подготовка;
её хеши нельзя заменять хешами чужого запуска.

```sh
uv run --no-sync coveo-recsys historical build --config configs/coveo_historical.json --run-id coveo-historical-ag10000-v1 --run-dir runs/coveo-historical-ag10000-v1
```

Готовый состав — `historical/package.json`; таблицы, массивы и отчёт сборки лежат
рядом в каталоге запуска. Сырые CSV поведения и поиска повторно не готовятся.
Код сборщика может отличаться от закреплённого кода подготовки.

Повтор проверяет входы и готовый пакет. При прерывании между опубликованными
частями вычисления повторяются, совместимые файлы не перезаписываются.
Восстановление с произвольной строки или ребра не поддерживается.
После изменения кода сборщика или его настроек нужен новый каталог запуска.

## Проверки и ограничения

Последний полный локальный прогон: 821 тест. Mypy, `ruff check .` и
`ruff format --check .` прошли. Остаётся предупреждение об устаревшем API в
зависимости Starlette. Wheel собран и установлен в чистое окружение; проверены
встроенные конфигурации, схемы и сборка исторического пакета на малом тестовом входе.

[GitHub Actions](/.github/workflows/checks.yml) при `push` и `pull_request` проверяет проект на Ubuntu: обычную установку пакета (`--no-editable`), форматирование и правила Ruff, типы, тесты без меток `coveo` и `load`, сборку и запуск консольной команды. Удалённый запуск ещё не проверен.

Реальный прогон 25 сентября 2026 года рассмотрел 5 010 682 сессии. Для A_G:
655 365 с первым допустимым запросом, 612 700 после календарного допуска,
10 000 выбраны по хешу. Их 108 800 исходных строк (107 158 поведения и 1 642 поиска)
сведены в 77 386 канонических блоков; сохранены 10 000 первых запросов.
Зарегистрированная цель есть у 137 сессий; 9 863 пустые цели имеют статус `unknown`.
Полнота телеметрии неизвестна для всех сессий.

В выбранном наборе 7 264 различных товарных SKU:

- 31 214 событий `detail`, 7 104 SKU; в двух и более сессиях просмотрены 3 607 SKU,
  в трёх и более — 2 176.
- 188 событий `purchase`, 158 SKU, 137 сессий. Покупки шести SKU зарегистрированы
  в двух и более сессиях, двух SKU — в трёх и более. В этом наборе все эти события
  попали в целевые окна; число событий не равно числу заказов.
- У 5 451 пары `(сессия, SKU)` есть просмотры в разных временных блоках.
  Исходные повторы одного события сюда не входят.

| Проверка | Время | Пик памяти процесса | Логические чтения CSV |
|---|---:|---:|---:|
| Малый A_G, 64 сессии | 975 с | 100,4 МиБ | 65,24 ГБ |
| Возобновление малого A_G после отбора | 370 с | 89,6 МиБ | 48,97 ГБ |
| Рабочий A_G, 10 000 сессий | 2 165 с | 844,8 МиБ | 65,24 ГБ |

Пик временного диска рабочего A_G — 467,4 МиБ, преимущественно SQLite; результат
перед записью измерений — 501,7 МиБ и 200 272 файла вместе с копиями и журналами.
Наибольший зафиксированный расход памяти пришёлся на публикацию общего отчёта,
не на потоковое чтение CSV. Чтения включают два
прохода поведения/поиска и проверки хешей; это логический объём, не физический
обмен с диском в обход кеша ОС. Прогон завершился за 36 минут в установленных пределах.

Рабочий результат — `runs/coveo-ag10000-observed-v1/`, вне Git. Полный повтор
на 10 000 сессий не выполнялся. Прерывание и восстановление проверены на малых
тестах после изменения кода и ранее на реальном наборе из 64 сессий.

Независимый пересчёт 30 001 Parquet подтвердил сводку, допуск, происхождение,
первые запросы и цели всех 10 000 сессий. Отдельный проход CSV сверил 81 строку
восьми сессий, заранее выбранных по хешу; 192 таблицы прежних 64 сессий совпали
побайтово. Подтверждения — `preparation/composition_check.json` и
`preparation/independent_check.json` рабочего запуска. Эти проверки выполнялись
после подготовки и не входят в её время в таблице.

Прежние `runs/coveo-ag64-observed-v1/` и `runs/coveo-ag64-observed-v1-resumed/`
сохранены: 739 исходных строк, 530 блоков, одна сессия с целью, около 3,45 МиБ результата.
Независимая сверка подтвердила исходные строки малого набора, а после реального
прерывания совпали 195 файлов. Это результаты прежнего объёма, не измерения текущей конфигурации.

Исторический пакет построен на всех 10 000 сессиях в
`runs/coveo-historical-ag10000-v1/`. Каталог содержит 7 264 SKU.
При минимальной поддержке в трёх сессиях:

| Отношение | Рёбра после поддержки / разреживания | SKU с исходящими связями | Доля каталога |
|---|---:|---:|---:|
| `detail → detail` | 1 513 / 1 513 | 616 | 8,48% |
| `detail → add` | 2 / 2 | 2 | 0,028% |
| `detail → purchase` | 0 / 0 | 0 | 0% |

Пригодны векторы описаний 7 112 товаров и изображений 7 000; остальные отсутствуют.
Сборка обработала 80 475 промежуточных пар, максимальная одновременная группа —
4 события. Полный пересчёт при возобновлении занял 219 с, пик памяти — 190,1 МиБ,
временный диск графа — 3,1 МиБ. Повторная проверка готового пакета заняла 66 с.
Каталог запуска после проверок занимает 14,5 МиБ в 166 файлах, включая
дескрипторы, служебные копии и отчёты; входной A_G сюда не входит.

Прерывание после публикации графа не оставило маркера готовности. После возобновления
и повторной команды совпали 36 отпечатков математических данных; 23 ранее
опубликованные части не изменились. Подтверждения — в `checks/` каталога пакета,
измерения — в `historical/build_report.json` и `historical/executions/`.
Независимый пересчёт всех сессий подтвердил каталог, графы, статистики и метаданные
с допусками `atol=1e-10`, `rtol=1e-8`; результат — `checks/independent.json`.

Покрытие подтверждает необходимость расширения A_G в Э2-08 до признаков B
и обучения. Пороги графа не снижались; полный объём Coveo не подготовлен.
Покрытие графа не является качеством рекомендаций: модели и выдачи ещё нет.

Численные свойства проверяются независимыми эталонами: не менее 1000 примеров на свойство, seed 17. Соответствие реализованных проверок требованиям хранится в [реестре](/configs/test_registry.json); результат выполнения показывает `pytest`. B03.service, полный B05/B10 и независимость полного ответа от поисковых списков в B02 остаются на следующих этапах.

Обучение и оценка на Coveo, нагрузка и A/B не проводились. Значения качества, задержки и потребления памяти рекомендательной системы не измерены. Числа в спецификации — требования и расчётные примеры.

Основная метрика — Hit@20: доля сессий с зарегистрированной будущей покупкой, в которых первая выдача содержит хотя бы один целевой SKU. Цель включает все различные SKU зарегистрированных покупок после первого запроса в установленном окне той же сессии. Метрика не измеряет прирост покупок от рекомендаций; для такого вывода нужен эксперимент с показами.
