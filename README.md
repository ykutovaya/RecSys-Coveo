# Сессионные рекомендации на данных Coveo

Проект рекомендательной системы для интернет-магазина: по просмотрам и поиску в анонимной сессии подобрать товары, которые пользователь может купить до её завершения.

Реализованы основа проекта, подготовка искусственных данных Э1 и проверка поставки Coveo. Рекомендации пока не выдаются: графа, обучения и сервиса нет. Формат поставки подтверждён; полнота телеметрии и допуск реального запуска — нет.

## Задача и данные

Планируемая система отбирает до 300 кандидатов и возвращает до 20 различных допустимых товаров. Обучение использует последующие покупки той же сессии; будущие события не должны попадать в признаки.

Источник — Coveo SIGIR eCom Data Challenge: `browsing_train.csv`, `search_train.csv`, `sku_to_content.csv`. Исходные данные не включены в репозиторий.

Первый вариант — GCS+Rk: граф связей товаров, раздельные сходства описаний и изображений, поисковый контекст и ранжировщик на LightGBM с собственными производными. Нейросеть, ANN и реальный A/B — последующие этапы.

## Что работает

- Неизменяемые типы префикса, отдельные цели и веса, строгая сериализация UTF-8 и int64.
- Устойчивые численные функции, нормировка векторов, проверяемая арифметика времени, агрегация последней группы.
- Локальные артефакты с хешами и зависимостями; Parquet и числовые матрицы без `pickle`.
- Схемы паспорта и признаков, реестр 30 нормативных проверок и EXPL01.
- Проверка допуска по паспорту 2.10 с протоколом `observed_purchases_v1` и результатам этапов. Проверки кода запускаются через `pytest` и не заменяют допуск фактического запуска.
- Порционное чтение CSV, внешняя сортировка и канонизация полных блоков с происхождением и кратностями.
- Видимые префиксы по двум временам, корзина, поисковый контекст и расписание запросов.
- Семь периодов, воспроизводимый отбор целых сессий, явное покрытие, отдельные цели и когорта первого просмотра.
- Статическая проверка `sealed_block_v1`; сохранение и возобновление подготовки с проверкой хешей.
- Проверка общих зависимостей один раз за операцию и свежий заключительный обход перед успехом.
- Отдельная потоковая проверка трёх исходных CSV Coveo: схема, время, векторы, размеры и SHA-256 без подготовки сессий, целей и показателей покупок.

Условия стадий паспорта проверяются отдельно от исполнения тестов; локальная оценка не требует готового сервиса. Искусственные отчёты отделены от результатов на Coveo. Точные столбцы признаков остаются Э3, функция производных ранжировщика — Э4.

## Запуск Э0

Нужны Python 3.11.9 и uv 0.10.4. Из корня проекта:

```sh
uv sync --locked
uv run --no-sync coveo-recsys environment
uv run --no-sync ruff format --check .
uv run --no-sync ruff check .
uv run --no-sync mypy
uv run --no-sync pytest -m "not coveo and not load"
```

Версии и хеши закреплены в [uv.lock](/uv.lock), состав зависимостей — в [pyproject.toml](/pyproject.toml). Базовая установка не включает PyTorch и не требует GPU; необязательный CPU-профиль устанавливается через `uv sync --locked --extra neural`.

Создание и проверка паспорта:

```sh
uv run --no-sync coveo-recsys manifest init --run-id e0 --run-dir runs/e0
uv run --no-sync coveo-recsys manifest validate --manifest runs/e0/manifest.json --run-dir runs/e0 --stage preflight
```

Последняя команда должна отказать в допуске: у проекта паспорта нет фактических данных и полного набора обязательных результатов. Успех проверок кода не означает успешный `preflight`.

Паспорт сохраняется в `runs/e0/manifest.json`, вне Git; повтор `manifest init` его не перезаписывает. После изменения закреплённых кода, входов или настроек нужен новый запуск. Команды `historical`, `train`, `serve` и остальные будущие этапы возвращают явный отказ.

Используется один паспорт, результаты стадий хранятся отдельно. До открытия соответствующих оценочных данных фиксируется план; при проверке его закреплённый хеш передаётся через `--plan-reference NAME=SHA256`. Неподтверждённые флаги успеха не дают допуска. Прежние форматы паспорта не поддерживаются.

## Подготовка данных Э1

Пример использует только [искусственные CSV](/tests/fixtures/e1/), [профиль](/configs/synthetic_csv.json) и [план](/configs/synthetic_preparation.json). Это не описание реального формата поставки Coveo.

```sh
uv run --no-sync coveo-recsys data inspect --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --run-id e1 --run-dir runs/e1
uv run --no-sync coveo-recsys data prepare --input-dir tests/fixtures/e1 --profile configs/synthetic_csv.json --plan configs/synthetic_preparation.json --run-id e1 --run-dir runs/e1
```

Ожидается: 3 сессии, 9 канонических блоков, 4 запроса у `s1` и `s2`; `s3` исключена из-за покупки в первом блоке. Цели `s1` содержат `B`, цели `s2` пусты. Итог — `runs/e1/reports/preparation.json`, отдельные таблицы — в `datasets/`, журнал хода выполнения — в `preparation/progress/`.

Повтор `data prepare` с теми же входами проверяет сохранённые зависимости. После прерывания используется совместимый канонический индекс; завершённые файлы не перезаписываются. Изменённые входы, код, план или повреждённые файлы дают отказ. Для чтения подготовленных наборов предусмотрен [DatasetAccess](/src/coveo_recsys/data/access.py): A_N и закрытые периоды не открываются прямым путём через этот интерфейс, цели нельзя прочитать как префиксы.

Контракты имеют версию 2; старые записи версии 1 нужно перестроить. Зрелость при задержанной доставке не вычисляется без истории подтверждения полноты; её проверка в Э1 ограничена историческим `a=t`. Защита рабочей СУБД и квитанции остаются Э6. Повторные обходы общих зависимостей устранены; кеш действует только внутри одной команды. Расходы подготовки большой выборки ещё не измерены: проверка формата Coveo не выполняет канонизацию и расчёт целей.

## Проверка поставки Coveo

Исходные CSV размещаются в `data/01_raw/` и не входят в Git. Для полученной поставки используется [проверенный профиль](/configs/coveo_supply_v1.json):

```sh
uv run --no-sync coveo-recsys data inspect-supply --input-dir data/01_raw --profile configs/coveo_supply_v1.json --run-id coveo-supply --run-dir runs/coveo-supply
```

Команда читает все три файла, сверяет их размер и SHA-256, затем повторно хеширует входы перед публикацией. Сохраняет только структурную сводку и журнал ресурсов; строки, идентификаторы и векторы не выводит. При прерывании или повреждении незавершённого артефакта используйте новый `run-id` и каталог запуска, не перезаписывая прежний.

Формат трёх CSV подтверждён; покрытие телеметрии неизвестно. Проверка поставки не создаёт цели и не даёт допуска `preflight`.

### Малая подготовка реальных сессий

Адаптер использует те же канонизацию, расписание и расчёт целей, что и искусственный пример.
[План Coveo](/configs/coveo_preparation.json) закрепляет семь периодов, seed 17,
64 технические сессии и пределы: 30 минут, 512 МиБ памяти, 256 МиБ временных файлов.

```sh
uv run --no-sync coveo-recsys data prepare --input-dir data/01_raw --profile configs/coveo_supply_v1.json --plan configs/coveo_preparation.json --run-id coveo-ag64 --run-dir runs/coveo-ag64
```

Сначала выбираются минимальные хеши ID с любой строкой в A_G, затем читаются все
строки этих сессий из поведения и поиска, включая хвосты за границей периода.
Полные просмотры исходных файлов для отбора, проверки формата и хешей остаются необходимыми.
Это техническая выборка, не нормативный отбор допущенных сессий.

Цели со статусом `unknown` и запросы сохраняются в `diagnostic/A_G/`, канонические
блоки — в `canonical/`. Допущенный A_G и зрелая когорта не создаются. В материалах
[издателя](https://github.com/coveooss/SIGIR-ecom-data-challenge) описаны ограничения
отслеживания, а [статья авторов, §3](https://arxiv.org/html/2104.09423v4#S3) не уточняет
долю и единицу выборки. Ни конец CSV, ни отсутствие покупки не подтверждают полноту наблюдений.

`reports/preparation.json` со статусом `diagnostic_materialized` означает запись таблиц,
но не завершение команды. Итоговая проверка отмечается как `completed` в
`preparation/executions/`; там же — ресурсы, чтения и неудачные попытки.
Повтор сверяет исходники и переиспользует готовые стадии. Незавершённая сортировка
начинается заново, продолжения с последней строки CSV нет. После изменения кода
или плана нужен новый каталог запуска.

## Проверки и ограничения

Последний полный локальный прогон установленного wheel: 618 тестов. Mypy,
`ruff check .` и `ruff format --check .` прошли. Упакованный план Coveo и консольная
команда проверены без ссылки на исходники. Остаётся предупреждение об устаревшем
API в зависимости Starlette.

[GitHub Actions](/.github/workflows/checks.yml) при `push` и `pull_request` проверяет проект на Ubuntu: обычную установку пакета (`--no-editable`), форматирование и правила Ruff, типы, тесты без меток `coveo` и `load`, сборку и запуск консольной команды. Удалённый запуск ещё не проверен.

На реальной технической выборке 25 сентября 2026 года: 64 сессии, 586 исходных
событий, 418 канонических блоков, 150 запросов. Все 150 целей — `unknown`.
Исключения: 19 сессий без допустимого первого запроса, 41 с неподтверждённым
покрытием, 4 у границы зрелости. Допущенных сессий A_G — 0.

| Проверка | Время | Пик памяти процесса | Логические чтения CSV |
|---|---:|---:|---:|
| Первичная подготовка | 1715 с | 101 МиБ | 65,24 ГБ |
| Повтор готового запуска | 32 с | 64 МиБ | 24,52 ГБ |
| Возобновление с канонического индекса | 42 с | 84 МиБ | 32,70 ГБ |

Перед планированием отдельно просмотрены только временные метки: 263 с и 8,10 ГБ
чтений. Первичная подготовка включает проверку формата всех трёх CSV, два просмотра
поведения и поиска для отбора/сбора сессий и пять проверок хешей исходников.
Пик временных файлов сортировки — 1,08 МиБ; файлы первичного результата занимают
около 3,0 МиБ вместе с копиями и журналами, без накладных расходов файловой системы.
Объём чтений включает повторные проходы, а не физический обмен с диском в обход кеша ОС.

Для испытания прерывания восстановлена копия канонической контрольной точки
без итоговых запросов, целей и отчёта. Копирование 1,90 МиБ артефактов заняло 2,5 с;
исходные CSV не копировались. Прерванная попытка отмечена как `interrupted`,
а не как успех. Возобновление переиспользовало проверку формата, отбор ID и индекс,
заново рассчитало запросы/цели; все 196 сравниваемых файлов совпали с непрерванным
прогоном. Продолжение незаконченной сортировки этим испытанием не заявляется.

Локальные измерения и свидетельства покрытия сохранены в `runs/coveo-calendar/`,
`runs/coveo-ag64-20260925/` и `runs/coveo-ag64-20260925-resume/`, вне Git.
Это проверка подготовки, не качества рекомендаций или полной масштабируемости Coveo.

Полнота телеметрии остаётся неизвестной. Для продолжения на Coveo нужно перевести
подготовку на `observed_purchases_v1`: один запрос на сессию, зарегистрированные
будущие покупки как цель, без отрицательных исходов из отсутствующих записей.
Паспорт и его проверки уже обновлены; расчёт целей в подготовке — ещё нет.

Численные свойства проверяются независимыми эталонами: не менее 1000 примеров на свойство, seed 17. Соответствие реализованных проверок требованиям хранится в [реестре](/configs/test_registry.json); результат выполнения показывает `pytest`. B03.service, полный B05/B10 и независимость полного ответа от поисковых списков в B02 остаются на следующих этапах.

Обучение и оценка на Coveo, нагрузка и A/B не проводились. Значения качества, задержки и потребления памяти рекомендательной системы не измерены. Числа в спецификации — требования и расчётные примеры.

Основная метрика — Hit@20: доля сессий с зарегистрированной будущей покупкой, в которых первая выдача содержит хотя бы один целевой SKU. Цель включает все различные SKU зарегистрированных покупок после первого запроса в установленном окне той же сессии. Метрика не измеряет прирост покупок от рекомендаций; для такого вывода нужен эксперимент с показами.
