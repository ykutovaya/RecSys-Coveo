# Техническое задание: сессионная рекомендательная система Coveo

[English](/documents/en/implementation_spec.md) | Русский

Версия ТЗ: 1.8. Редакция: 8 октября 2026 года.

Основание: [математическая спецификация 2.10](/documents/math/coveo_session_recommender_math.tex) и [шаблон паспорта запуска 2.10](/documents/math/coveo_session_recommender_run_manifest.template.json).

ТЗ определяет требуемые интерфейсы, результаты и условия приёмки. Формулы и обозначения приведены в спецификации; `sec:...`, `eq:...`, `app:...` — её метки. Реализованные возможности описаны в [README](/README.ru.md). Используется единый формат паспорта 2.10 с `evaluation_protocol="observed_purchases_v1"`; прежние форматы не поддерживаются.

При противоречии приоритет имеют формулы и нормативные условия спецификации, затем заполненный и проверенный паспорт запуска. Противоречие фиксируют и устраняют до начала затронутого этапа; менять алгоритм без явного указания нельзя. Паспорт задаёт разрешённую конфигурацию, но не отменяет требования.

## 1. Назначение и границы реализации

Реализовать воспроизводимую систему: по доступному префиксу анонимной сессии отобрать до 300 кандидатов, ранжировать их и вернуть до 20 различных допустимых товаров. Протокол оценивает только первую выдачу по всем различным SKU зарегистрированных будущих покупок в окне той же сессии. Основная метрика — Hit@20 среди сессий с непустой зарегистрированной целью. Полнота телеметрии неизвестна; метрика не измеряет частоту покупок во всех сессиях или прирост конверсии.

### 1.1. Состав поставки

| Часть | Результат |
|---|---|
| Первый локальный запуск | Подготовка данных, граф и справочники A_G, точный отбор, признаки, GCS+Rk, воспроизведение и отчёт C_smoke. |
| Итоговая историческая оценка | Зафиксированный выбор, вариант без метаданных, однократная оценка на D с интервалами и статусами достаточности. Не требует готовности сервиса. |
| Демонстрационный сервис | Один локальный процесс: API на готовой модели, проверка входных данных, состояние, повторы, резерв, объяснения и журнал. Приёмка — §10.6. Промышленная эксплуатация не входит в обязательную поставку. |
| Исследования и A/B | Только по отдельной задаче после базовой оценки; условия включения — §§12–13. |

Первый запуск — одна конфигурация `gcs_rk_v2_7`, без подбора параметров. Нейросеть, SID, ANN, обновляемый граф, разнообразие, IPS/DR и A/B в него не входят. Периоды A_N и E остаются зарезервированными: их нельзя присоединять к другим периодам.

Вариант без предоставленных метаданных должен быть готов к D для проверки чувствительности, а не для выбора второго победителя; первый C_smoke можно провести до его реализации. Контрольные методы первой оценки — популярность A_G и последние просмотры с дополнением списка популярными товарами. Диагностические G, GC, GCS допустимы на C_smoke; полный набор исследовательских сравнений не требуется.

### 1.2. Что не входит в задачу

- Восстановление отсутствующих цен заказов, маржи, устойчивого ID человека, вероятностей показа или исторических версий векторов.
- Обучение собственных текстовых и визуальных моделей на сырых данных, которых нет в Coveo.
- Гарантированный положительный бизнес-эффект.
- Автоматическое переобучение по тревоге, непрерывная оптимизация по D, поиск конфигураций до получения удобного результата.
- Полноценная распределённая платформа, оркестратор кластеров и интерфейс магазина. Код интеграции с ними должен находиться вне вычислительного ядра.

## 2. Архитектура и общие требования

### 2.1. Разделение кода

Границы модулей и направления зависимостей заданы в [архитектуре](/documents/architecture.md#3-границы-модулей-и-зависимости). Обучение и обслуживание используют общий расчёт признаков; вычислительное ядро не зависит от HTTP, хранилища состояния или формата отчёта. Модули поздних этапов не требуется создавать заранее.

### 2.2. Среда и зависимости

- Базовая математика и метрики — NumPy/FP64; ранжировщик — `lightgbm.train`, LightGBM 4.6.0.
- Для нейросетевого профиля — NumPy 2.1.3, PyTorch 2.6.0, CPU/FP32, один вычислительный и один межоперационный поток, детерминированные алгоритмы.
- Версии Python, библиотек для работы с таблицами, статистики, JSON Schema, HTTP, тестов, компилятора и численных библиотек закрепить на Э0. Проверить совместимость на минимальном примере; точные версии и хеши сохранить в файле зависимостей. Зависимости без закреплённых версий запрещены.
- Необязательные нейросетевые зависимости устанавливать отдельным набором. Базовый запуск не должен импортировать PyTorch или требовать GPU.
- ОС, CPU, процессы, потоки и измеритель памяти узла нагрузочных испытаний фиксируются отдельно от среды разработчика.
- Эталонные тесты запускаются без исходных данных Coveo. Испытания на Coveo и нагрузочные испытания отмечаются отдельно; пропуск из-за отсутствия данных не считается успешным прохождением.

### 2.3. Главные интерфейсы ядра

```text
canonicalize(raw_events, event_semantics) -> CanonicalSession
make_schedule(session, task_config) -> RequestContext[]
make_targets(session, schedule, period) -> TargetRecord[]
build_historical(admitted_A_G, metadata, config) -> HistoricalPackage
retrieve(context, historical_package, source_runtime) -> CandidateResult
build_features(context, candidates, historical_package) -> FeatureBatch
fit_ranker(training_groups, ranker_config) -> RankerArtifact
recommend(context, package, execution_context) -> RequestResult
explain(trace, recommendation_items, templates) -> Explanation[]
reduce_state(state, accepted_block, config) -> StateTransition
evaluate(request_results, registered_targets, frozen_plan) -> EvaluationResult
validate_manifest(manifest, stage, artifacts) -> ValidationResult
```

`RequestContext` содержит доступный префикс, времена, допустимый каталог и версии, но не будущие цели или принадлежность сессии положительной когорте. Обучающие веса и метки передаются отдельно, только при пакетной обработке. `execution_context` содержит срок, выбранную ветвь, состояние источников и обязательной записи, но не будущие покупки.

Принадлежность списку источника и доступность балла — разные поля. Различать причины пустого источника, отсутствующей модальности, выключенного модуля и технического отказа.

## 3. Данные и сохраняемые артефакты

### 3.1. Входные файлы

Поддержать `browsing_train.csv`, `search_train.csv`, `sku_to_content.csv`. По фактическим файлам закрепить в схеме имена и смысл обязательных столбцов. Единицы времени, размерности векторов и смысл дубликатов необходимо подтвердить.

Нормативные соответствия: `server_timestamp_epoch_ms` — время события в целых миллисекундах; `product_action` — товарное действие; `query_vector` — поисковый вектор; `description_vector` и `image_vector` — разные товарные модальности. `product_skus_hash` и `clicked_skus_hash` не заменяют датированные события. Поддержать типы detail, add, remove, purchase, search, page; товар может отсутствовать у поиска и страницы без товара. Поля ID, категории и ценовой группы связать с фактической схемой файлов без догадок о кодировке.

Исходные файлы не изменять. Сохранить размер, SHA-256 точных байтов, версию, схему, диапазон записанных событий и известные разрывы. Читать порциями, без загрузки всех исходных таблиц в память. Полнота чтения опубликованных строк и полнота телеметрии — разные признаки; последняя сохраняется как `unknown`.

До открытия оценочных периодов разрешены необходимые проверки формата и целостности. Исходы D, показатели качества и сравнения политик на D не используются для выбора параметров, границ периодов или длины статистического блока.

### 3.2. Логические структуры

| Структура | Основные поля и ограничения |
|---|---|
| RawEvent | Пространство источника, сессия, ID события, время события, время доступности, тип, SKU или данные поиска; ссылка на исходную строку/байты. |
| CanonicalBlock | Сессия, точное время группы, канонические события, сырые кратности после удаления повторных ID, данные поиска и причины их непригодности. |
| SessionRecord | Время первого запроса и последнего записанного события, период, календарный допуск, полнота чтения строк, неизвестная полнота телеметрии, причина исключения. |
| RequestContext | request_id, session_id, trigger_block_id, t_q, a_q, номер допустимого запроса, видимый префикс, состояние корзины и поиска, версия префикса. |
| TargetRecord | request_id, множество зарегистрированных покупок Y_q, границы окна и принадлежность положительной когорте. Пустая цель не доказывает отсутствия покупки. |
| CandidateResult | Упорядоченные результаты источников, итоговые различные SKU, ранги и сведения о происхождении, маски доступности, квоты, причины отказов, выбранная ветвь. |
| FeatureBatch | request_id, SKU, матрица числовых и категориальных признаков в фиксированном порядке, маски, feature_schema_sha256. |
| SupervisionRecord | Кандидатные метки и парные веса для единственного запроса сессии с непустой целью; недоступна сервису. |
| RequestResult | Версия пакета, фактически выбранные кандидаты и ветвь, доставленный список, баллы, объяснения, статус доставки, причины, измерения времени, ссылка на трассу. |
| Explanation | SKU, ветвь, версия пакета и шаблона, источники и расчётная опора по §10.7; безопасная публичная форма отделена от внутренней диагностики. |
| SessionEvaluation | s, принадлежность положительной когорте, V_s, U_s, Hit_s первой выдачи, календарная ячейка и заранее заданные разрезы. Сессия без цели не становится промахом. |
| MetricResult | Значение либо null, статус, причина, единица, знаменатель, счётчики, интервал и его предпосылки/пригодность. |

Время события и доступности — int64 в миллисекундах UTC; счётчики — int64. Проверять переполнение счётчиков и временных разностей; секунды переводить в миллисекунды явно. ID хранить без потери исходных UTF-8 байтов, сортировать по нормативному порядку, не по локали.

Предлагаемые форматы: Parquet для нормализованных таблиц; массивы с явными dtype, формой и порядком строк — для матриц. Кодеки закрепляются в среде. Сериализация сохраняет кратности, порядок ID, точность времени и признаки неизвестности.

### 3.3. Каталог запуска

Каждый запуск хранится отдельно. Один паспорт содержит закреплённые входные данные, версию кода, зависимости, настройки и ссылки на результаты. Планы выбора и оценки фиксируются до открытия соответствующих данных (§4); результаты не меняют планы.

```text
runs/<run_id>/
  manifest.json            конфигурация и идентификация входов
  plans/                   зафиксированные планы выбора и оценки
  historical/              каталог, графы, частоты, словари, векторы
  datasets/<period>/       запросы и признаки; цели — отдельно
  models/                  ранжировщик
  results/                 метрики и результаты проверок
```

Каталоги создаются по мере расчёта; готовый пакет для сервиса оформляется по §10.4. Промежуточные файлы не требуют отдельных паспортов, схем и хешей, если контракт потребителя не предусматривает использование этих файлов. Общий реестр артефактов, граф зависимостей и кэш не обязательны.

Файл записывается по временному пути и публикуется после проверки, без перезаписи прежнего результата. Набор считается готовым после записи всех обязательных файлов. Перед повторным использованием необходимо проверить полноту и совместимость входных данных, кода, настроек и форматов; иначе выполняется новый расчёт.

Исходные CSV не копируются в каталог запуска. Указать их расположение и порядок очистки промежуточных данных и трасс. Удалённые входные данные нельзя восстановить по хешу. Отдельная система доступа и удаления для локальных расчётов не нужна; требования рабочего сервиса — в §11.2.

## 4. Паспорт запуска и управление этапами

Основание: `app:run-manifest`, `app:run-stages`, B13.

JSON Schema проверяет структуру паспорта; смысловые проверки — входные данные, временные границы, совместимость модели и условия текущего расчёта. Шаблон `template_not_runnable` нельзя использовать для запуска; неизвестные значения нельзя заменять вымышленными.

Один паспорт описывает запуск. Результаты этапов сохраняются отдельно; новый снимок паспорта и отдельный SHA-256 на каждой стадии не требуются. При изменении закреплённых входных данных, кода или настроек создаётся новый запуск.

| Условие | Что проверяется |
|---|---|
| preflight | Входные файлы, схема, периоды, код, настройки используемых модулей и ранние проверки данных. Модели, плановые параметры точности D и будущие отчёты не требуются. |
| post_training | Модель, схема признаков, применимые проверки математики, разделения данных и отключения калибровки. Сервис и A/B не требуются. |
| pre_selection | До открытия C_select закреплены варианты, бюджет и правило выбора; обучение и относящиеся к оценке проверки завершены. |
| pre_D | Зафиксированы политика либо пара, план оценки и проверки чувствительности: полуширина в долях, плановая дисперсия, допущения и множитель зависимости, происхождение пилотного расчёта C_smoke, сетка и блоки; выполнены выбор и применимые проверки. Результатов D ещё нет, E не используется. |
| post_D | Оценки, интервалы и фактические статусы; план не изменён. |
| post_load | Только для промышленного профиля: нагрузка, память, задержки, отказы и восстановление; не требуется для демонстрации §10.6. |
| pre_AB / post_AB | Допуск и результаты рабочего эксперимента по §13; требуют принятого сервиса. |

Планы C_select, D и A/B сохраняются неизменяемыми; результат ссылается на использованный план и его хеш. План D связывает выбранную модель, отчёт выбора и план C_select. Сам по себе хеш не подтверждает, что план был принят до просмотра данных: это обеспечивает порядок запуска и запрет чтения закрытых периодов.

Локальная оценка `ideal_deterministic` не зависит от post_load и не подтверждает готовность сервиса. Оценка по `execution_trace` требует проверенного сервиса и полной трассы. Общая команда не открывает C_select или D автоматически; E остаётся закрытым.

Поля `serving` и `operations` паспорта описывают отложенный промышленный профиль. Его сроки и `post_load` не применяются к демонстрации §10.6: общий тайм-аут задаётся настройкой локального запуска. Формат паспорта не меняется; применимые проверки корректности выполняются, но их прохождение не означает прохождения всей промышленной приёмки.

Отсутствующий обязательный результат — `not_run`, нарушение — `failed`, неприменимый модуль — `not_used` с причиной. Применимость определяется профилем запуска и выполняемым расчётом, а не желанием пропустить проверку. Итоговые состояния — по §17.2.

## 5. Подготовка событий, запросов и целей

Основание: `sec:data`, `sec:time`, `sec:requests`, `sec:eval-observed`; B01–B03, B06, B10.data.

### 5.1. Импорт и канонизация

1. Проверить файлы и их схему. Объединить события поведения и поиска по сессии и точному времени.
2. Для действий с товарами использовать product_action; сопутствующий pageview не учитывать как второй просмотр товара.
3. По устойчивым транспортным ID удалить подтверждённые повторные доставки. Без такого ID совпадение полей не доказывает повтор. Технический ID исходной строки не восстанавливает порядок событий.
4. В `set_v1` одинаковые (сессия, время, товар, действие) свести к одному событию, сохранив исходную кратность и происхождение.
5. Формировать полные блоки одновременных событий. Перестановка исходных строк внутри блока не меняет результат.
6. В историческом режиме использовать a=t. Рабочий адаптер передаёт только принятые полные блоки и серверное время доступности.

Поисковые векторы сравнивать до нормировки по FP64-координатам; +0 и −0 равны. Хранить различные исходные векторы, кратности и маркеры отсутствия/непригодности. Разные векторы с одинаковым нормированным направлением не сливать. Списки product_skus_hash и clicked_skus_hash не входят в основной контекст.

Последний поисковый блок пригоден при единственном корректном значении без маркеров непригодности; повторы этого значения допустимы. Иначе контекст отключается без возврата к более раннему поиску.

Для воспроизводимой подвыборки в каждом периоде вычислять SHA256(uint64_be(seed) || uint64_be(длины ID в байтах) || utf8(ID сессии)), сортировать по хешу, затем UTF-8 ID. Начальное состояние — 17. Число сессий задать до отбора; сохранить все их строки, без предпочтения покупающих.

На C_smoke провести предусмотренную проверку чувствительности `multiset_v1`: кратности влияют на счётчики, историю и средние, но цели остаются множествами, а поддержка графового ребра — числом различных сессий.

### 5.2. Префикс и расписание

Первый запрос — после первого блока с корректным товарным detail, если покупка не наблюдалась ни ранее, ни в этом блоке.

Для каждого метода Q_max=1: последующие блоки не создают запросов в этом эксперименте, но остаются в журнале для расчёта целей. Момент запроса не зависит от будущей покупки, наличия метаданных или непустого ответа. Непригодный поисковый вектор отключает источник, но не меняет допуск.

Префикс содержит только события той же сессии с t(e)≤t_q и a(e)≤a_q. Артефакт отбора должен быть опубликован строго до t_q.

Раздельно хранить последние 20 detail, последние 20 общих блоков, полную последнюю группу detail, счётчики видимого префикса, последние просмотры товаров и поиск. При усечении равенство времён разрешать порядком ID, не считать его причинным.

Состояние товара в корзине — add/remove/unknown, начальное значение — unknown. Последняя однозначная группа задаёт add/remove, одновременные add и remove — unknown. Повторные удаления не создают отрицательного количества. Наблюдаемое состояние не гарантирует соответствия фактическому содержимому корзины.

### 5.3. Зарегистрированные цели и календарный допуск

Начальные H=86400 с, g=1800 с. Для допущенной сессии τ_s=min(t_0,s+H, t_last,s^obs), где t_last,s^obs — последнее записанное событие объединённого потока поведения и поиска. Цель Y_q — все различные SKU зарегистрированных покупок той же сессии в (t_0,s,τ_s], а не первая или последняя покупка. Повторы SKU не увеличивают цель; правая граница включается.

Допуск в период [a_J,b_J): t_0,s∈[a_J,b_J) и строгое t_0,s+H+g<b_J — независимо от покупки. Для A_G дополнительно t_last,s^obs+g<b_AG; сессия с поздним хвостом исключается целиком. Границы и размеры подвыборок фиксируются до анализа целей. Все опубликованные строки выбранной сессии читаются полностью; пропущенные строки — ошибка подготовки, не неизвестность телеметрии.

Последняя запись и запас g не доказывают завершения сессии. При неизвестной полноте телеметрии непустые цели пригодны для условной оценки, а пустые не означают отрицательного исхода сессии. Покупка вне I_G остаётся в цели и знаменателях. Добавлять целевой товар в кандидаты запрещено.

Результат этапа: канонические блоки, причины допуска/исключений, первый запрос и его контекст, отдельные зарегистрированные цели, числа подходящих N_eligible, сохранённых N_obs и целевых N_+ сессий. Результат отбора N_+ не используется при отборе кандидатов, расчёте признаков или принятии решения о выдаче. Для A_G и измерения ресурсов используются также сессии без цели.

Критерии: B01, B02, B03.data, B06, B10.data; тесты границ времени, покупки в первом блоке, нескольких покупок и повторов SKU, пустой цели при неизвестной телеметрии, пропуска опубликованных строк и изменения будущего при неизменных входных данных из прошлого.

## 6. Исторический пакет A_G

Основание: `sec:model-graph`, `sec:model-content`, `app:first-config`; B04, B05, B09, B10.

### 6.1. Каталог, граф и статистики

Строить I_G по всем сохранённым сессиям A_G после допуска §5.3, не только по сессиям с покупкой. События последующих периодов не расширяют каталог, граф, словари или исторические статистики базовой модели.

Три направленных отношения: detail→detail, detail→add, detail→purchase. Разные товары, строго более поздняя товарная группа, расстояние 1…10 групп и задержка 0<Δt≤1800 с. Исключить петли и одновременные переходы; группы без товарных событий в расстояние не входят.

Для каждой (сессия, отношение, i,j) взять максимум exp(−Δt/600), затем сложить вклады сессий. Поддержка — число сессий с допустимой парой, не повторов. Эквивалентно можно хранить минимальную допустимую задержку пары в сессии.

Порядок обработки:

1. Удалить рёбра с поддержкой <3.
2. В каждой строке и отношении оставить до 100 рёбер по убыванию веса, затем ID.
3. Нормировать сохранённые веса; пустая строка нулевая.
4. Сохранить d_i как сумму оставленных весов и ρ_i=d_i/(d_i+10).

Хранить P, W, поддержки, суммы строк, ρ и соответствие ID разреженно, без плотной матрицы каталога. Стоимость промежуточной агрегации и максимальная временная группа учитываются отдельно от размера графа.

Популярность — число различных сессий A_G с detail товара; сглаживание η_P=1. Отдельно хранить число различных сессий A_G с зарегистрированной покупкой товара: повторные покупки в сессии не увеличивают счётчик. Эти статистики описывают зарегистрированные события, а не вероятность покупки.

Историческая частота покупок исключена из схемы признаков по §8.4. Когорта первого просмотра, её знаменатели и сглаживание не рассчитываются.

### 6.2. Представления и численная устойчивость

Векторы описания, изображения и поиска нормировать отдельно. Совпадение размерностей не разрешает складывать разные пространства. Сходство поиска с описаниями товаров определяется контрактом происхождения пространств.

Норма вычисляется с масштабированием по максимальной абсолютной координате. Порог ε_v=10⁻¹²:

- отсутствующий вектор → маска 0, vector_absent;
- неправильная размерность, тип или неконечные координаты → маска 0, vector_invalid;
- малая/нулевая норма → маска 0, vector_zero;
- пригодный вектор → единичное направление и маска 1.

Непригодная внешняя модальность не отключает пригодные ветви. Внутренний NaN/Inf не маскировать: обучение завершается ошибкой, сервис переходит к предусмотренному резерву.

Реализовать общие устойчивые softplus, sigmoid, LSE/log-softmax, масштабированную норму и компенсированную сумму. Маски применяются до максимума; пустая область обрабатывается отдельной ветвью.

В B04 проверить малое время затухания: exp(−800) обнуляется в FP64, но математическая поддержка сохраняется. Совместно проверять поддержку, веса и нормировку; обеспечить устойчивый расчёт либо завершать его ошибкой до появления 0/0. Начальное τ_G=600 с не менять.

## 7. Кандидаты и признаки

### 7.1. Точный отбор

Основание: `sec:model-candidates`; B07, B08.

Использовать I_q=I_G без уже наблюдавшихся купленных товаров. Просмотр или добавление в корзину товар не исключает.

| Источник | Квота |
|---|---:|
| detail→detail | 50 |
| detail→add | 50 |
| detail→purchase | 50 |
| Описание | 40 |
| Изображение | 30 |
| Поиск | 50 |
| Недавние различные просмотры | 20 |
| Популярность | 10 |
| Сумма | 300 |

История ограничена L_H=20, затухание τ_H=300 с. Графовые баллы по каждому отношению — взвешенная сумма ρ_i·P_ij. Представления истории для описания и изображения нормировать независимо, по пригодным векторам. Нулевая сумма, в том числе при противоположных векторах, означает отсутствие источника.

Поиск использует последний доступный поисковый блок. Непригодность или возраст >600 с отключают источник без возврата к предыдущему блоку. Первый запуск — точный поиск по всем допустимым пригодным векторам. Допускается блочное умножение матриц с точным общим Top_m и единым разрешением равенств.

После объединения удалить дубли, сохранить все сведения о происхождении и дополнить список популярными товарами до M=300. Это дополнение отмечается как отдельное происхождение без ограничения квотой популярности 10. Недоступный источник не заполнять товарами с вымышленным баллом. При малом каталоге кандидатов будет меньше.

Для кандидата различать принадлежность списку источника, доступность балла и наличие ранга. Измеримый балл рассчитывать и вне квоты. Ранг r≥1 кодировать как 1/(1+r); отсутствующий — 0 с отдельной маской.

### 7.2. Схема признаков

Основание: `sec:model-features`. До обучения зафиксировать `feature_schema`: имя, позиция, тип, формула/метка TeX, маска, преобразование, происхождение и период подгонки каждого столбца. Состав столбцов определить по семействам и формулам спецификации.

Обязательные семейства:

- графовые баллы по отношениям, связи с последней группой, поддержка и маски;
- сходства описания/изображения с историей и последней группой;
- поиск, его давность и маски;
- число и давность просмотров кандидата;
- наблюдаемая корзина и давность;
- счётчики и длительность доступного префикса;
- категория, сходство категорий, порядковая ценовая группа и групповые сравнения;
- популярность и отдельное число сессий A_G с зарегистрированной покупкой товара;
- сведения о происхождении, исходные баллы и обратные ранги источников.

Групповые признаки — по всей последней группе detail. Среднее: Σn_j·M_ij·φ(i,j)/Σn_j·M_ij; n_j=1 для set_v1, кратность для multiset_v1. При нулевом знаменателе значение и маска нулевые. Максимумы от кратностей не зависят.

Сходство категорий — длина общего начального пути, делённая на максимум длин путей и единицы. Категория — единственный столбец базовой модели, обрабатываемый как категориальный: словарь A_G в UTF-8-порядке, неизвестное значение 0, известные 1,2,… . ID товара — не числовой признак. Ценовая группа — порядковая величина с маской, не цена заказа.

Логарифмирование счётчиков и давностей допустимо только как заранее зафиксированное преобразование. Изменение схемы признаков или отбора требует новых признаков B и ранжировщика.

Проверить затронутые части B01/B02/B05/B07–B10; полная приёмка — по §§15–16. Пакетный и последовательный расчёты совпадают по маскам, категориям, кандидатам и порядку точно. Для FP64-признаков проверять max_j |x_replay−x_serve|/(10⁻⁸+|x_replay|)≤10⁻⁶.

## 8. Ранжирование

### 8.1. Обучающая таблица

Основание: `sec:model-ranking`, `sec:model-ranker-implementation`.

Обучение использует только первые запросы сессий B с непустой зарегистрированной целью. Строка — фактический основной кандидат; метка — принадлежность Y_q. Не добавлять положительные товары извне кандидатов. Кандидаты вне Y_q — суррогатные отрицательные примеры, а не доказанные показы без реакции.

Запросы упорядочить по (session_id,t_q,request_id), товары — по UTF-8 ID. Одна сессия даёт одну группу; в Dataset.group передать размеры непустых групп. Пустой набор кандидатов не создаёт строк, но целевая сессия остаётся в знаменателе оценки. Группы без положительно-отрицательных пар имеют нулевые производные; при отсутствии пар во всей таблице данных недостаточно, обучение нельзя считать успешным. В первом запуске нет подвыборки отрицательных примеров.

До построения таблицы оценить верхнюю границу N_B^+·M строк, потребление памяти и место на диске. Таблицу можно строить порциями, но нельзя без явного указания заменять полное обучение последовательным дообучением на частях, сокращать каталог оценки или менять веса групп.

### 8.2. Собственные производные

`session_lambdas_v1` — вызываемая функция, а не строковая встроенная цель LightGBM. На каждой итерации:

1. Проверить конечность сырых баллов и пересчитать полный порядок группы по (−score,ID).
2. Построить все положительно-отрицательные пары.
3. Использовать сессионный вес 1, парный вес 1/max(1,|C⁺|·|C⁻|), бинарный IDCG@20 и Δ_ij по `sec:model-ranking`.
4. При фиксированных текущих рангах и парных весах накопить градиенты и диагональные вторые производные логистической потери, β_R=1.
5. Накопление — FP64, результат — непрерывные массивы FP32. Нулевые гессианы не заменять искусственным положительным порогом.

Пары ниже глубины имеют нулевой вес, но ранги строятся по всей группе; пары через границу не отбрасываются. Веса применяются один раз внутри функции, Dataset.weight=None. Встроенные параметры lambdarank не должны менять этот расчёт.

### 8.3. Настройки LightGBM и сохранение модели

Для профиля `gcs_rk_v2_7` закрепить все настройки `sec:model-ranker-implementation`: параметры модели, Dataset, обучения и предсказания, включая значения по умолчанию LightGBM 4.6.0. Идентификатор набора настроек не является версией протокола; соответствие проверяется до обучения.

Сохранить конфигурацию запуска, фактическое число деревьев и размеры листьев, хеш функции производных, схему признаков, порядок групп и статистику пар. Бюджет 200 не гарантирует 200 деревьев. Балл predict повторно на learning_rate не умножать; min_data_in_leaf не считать строгой гарантией фактического числа строк.

Исходный балл f_0=0. Имя категориального столбца передать в `categorical_feature`; в первом запуске не задавать монотонные ограничения, ограничения взаимодействий признаков и принудительные разбиения.

Основная выдача сортируется по убыванию f, затем ID; возвращаются первые min(20,|C_main|). Баллы не объявляются вероятностями покупки.

## 9. Временной протокол и историческая оценка

Основание: `sec:eval-temporal`, `sec:eval-offline`, `sec:eval-uncertainty`, `sec:metadata-sensitivity`, `app:diagnostic-output`.

### 9.1. Периоды и доступ к результатам

Семь непересекающихся частей: A_G → A_N → B → C_smoke → C_select → E → D. Хранить точные границы [a,b), принадлежность целой сессии и журнал открытия периодов.

- A_G: все сохранённые сессии после допуска §5.3; каталог, граф, популярность, счётчики зарегистрированных покупок, словари и масштабы.
- A_N: обучение включённых расширений; в базовой модели не используется.
- B: кандидаты фиксированного отбора и признаки; обучение своего ранжировщика для каждого варианта на сессиях с зарегистрированной целью.
- C_smoke: отладка, диагностика ошибок, стоимости и потерь охвата.
- C_select: один выбор из списка, зафиксированного до открытия. Новые варианты после просмотра не допускаются.
- E: резерв, в текущем протоколе не используется.
- D: одна итоговая оценка зафиксированного плана.

Предварительные календарные доли — 20/20/25/15/10/10%; C делится поровну по времени. Сетка не обязывает использовать непригодные периоды. Границы, потери H+g и число статистических блоков проверить до обучения по разрешённым ранним данным.

После доработки по результатам C_select этот период считается использованным для разработки; подтверждающий выбор требует нового периода. Расширение после оценки базовой модели на D требует нового итогового периода. Неиспользуемые A_N и E не становятся дополнительными данными базовой модели.

### 9.2. Метрики и диагностические таблицы

Публиковать N_eligible, N_obs, N_+ и причины исключений по §5.3. Основная оценка использует одинаковую для всех методов совокупность сессий с непустой зарегистрированной целью, N=N_+. Пустая выдача, отказ и резерв не удаляют такую сессию из знаменателя. При N=0 метрика равна null, статус — `insufficient`.

Обязательные расчёты:

1. Сессионный Hit_s — пересечение первой доставленной выдачи с зарегистрированной целью. Несколько попаданий не увеличивают вклад сессии.
2. Hit@20 = ΣHit_s/N в долях; парные разности с контрольными методами первой оценки из §1.1.
3. V_s — наличие цели в допустимом каталоге, U_s — наличие цели среди кандидатов выбранной ветви; кандидатная граница ΣU_s/N.
4. Проверка 1 ≥ V_s ≥ U_s ≥ Hit_s и точного разложения 1−Hit_s = (1−V_s)+(V_s−U_s)+(U_s−Hit_s). Средние потерь суммируются в 1−Hit@20.
5. Разделение отсутствия цели в историческом каталоге и недопустимости в конкретном запросе. Таблица отдельных покупок не подменяет сессионное разложение.
6. Кандидатный охват среди сессий с доступной целью; при нулевом знаменателе — неопределённое значение с причиной.
7. NDCG@K и Recall@K как вспомогательные показатели по правилам `sec:eval-diagnostics`; не заменять ими Hit@20.
8. Разрезы по длине истории, предшествующему поиску, корзине, популярности и известности товара, доступности модальностей. Границы групп популярности получаются из A_G.
9. Отдельные счётчики технических отказов, масок, превышений срока, резерва и отсутствующей трассы. Стоимость и отказы измерять также на сессиях без зарегистрированной цели.

Для источников сохранять размеры до/после квоты, глубину измеренного списка, пересечения, уникальные товары, охват и происхождение. Неизмеренный список не считать пустым. Пересечения усреднять по определённым первым запросам; долю пропусков показывать отдельно.

`Delta_fixed(source)` удаляет только товары без другого происхождения, без заполнения свободных мест и нового обучения. Исключение источника с перераспределением квот — отдельная конфигурация с собственным обучением. Общий охват нельзя получать сложением охватов источников.

### 9.3. Режим воспроизведения

Режим зависит от того, какая часть системы реализована:

- `ideal_deterministic`: a=t, фиксированные данные и исправные источники; результат относится к идеальному воспроизведению, а не к измеренным рабочим отказам.
- `execution_trace`: на сервисном этапе по фактической трассе `sec:ops-replay-trace` повторяет версии, доступность источников, выбранную ветвь, сроки и доставку. Не требуется для локальной оценки.

Названия режимов закрепить схемой. До реализации execution_trace исправный повтор расчёта нельзя выдавать за восстановление фактически использованного U_s. Неполнота трассы влияет на пригодность отчёта.

### 9.4. Интервалы и достаточность

Рассчитывать Hit@20 одной политики или парную разность на сессиях с зарегистрированной целью. Для основной оценки закрепить план учёта зависимости и вектор блочных сумм. Интервалы рассчитаны при условии регистрации покупки и не устраняют смещение из-за неполной телеметрии.

Основной алгоритм для Coveo:

1. Построить плотную сетку допустимых стартов [a_D, b_D−H−g), с заранее заданными началом и шагом. Число ячеек J должно быть целым. Пустые ячейки сохраняются, календарный запас H+g не добавляется.
2. Отнести целевую сессию целиком по t_0,s. Для пары сохранить в ячейке (Σd_s, n_j), где d_s = Hit_s(π₁)−Hit_s(π₀), n_j — число сессий с непустой целью. Для одной политики заменить d_s на Hit_s.
3. При длине блока m ячеек выбрать ceil(J/m) начал равновероятно из 1…J−m+1, склеить последовательные блоки, оставить J индексов.
4. Считать отношение сумм, а не среднее дневных Hit@20. Политики пары переносятся совместно.
5. Выполнить 2000 повторений, начальное состояние 17, α=0,05. Квантили — nearest-rank: элемент ceil(pB) отсортированных результатов.
6. При нулевом знаменателе хотя бы одного повторения не отбрасывать его: весь интервал получает `insufficient`.
7. Сохранить основной интервал, два заранее выбранных варианта длины блока, оценку погрешности моделирования границ и временной ряд.

Проверять как минимум 20 полных непересекающихся блоков и 20 непустых блоков. Для одной политики нужны по 100 попаданий и промахов среди сессий с целью, каждый класс не менее чем в 20 блоках. Для пары — не менее двух категорий из {−1,0,1}, каждая с 100 сессиями и присутствием в 20 блоках.

Нулевая эмпирическая вариация, совпадающие границы, неподходящие предпосылки или недостаточные значения счётчиков дают `insufficient`, даже если получен численный результат. Точечную оценку и причины сохранять. Дополнительные повторения не восполняют нехватку исходных блоков.

Для пригодного интервала проверить заданную полуширину в долях: `single_policy_half_width_fraction` для одной политики, `half_width_fraction` для пары. После обучения обосновать по разрешённому пилотному расчёту C_smoke положительный порог, плановую дисперсию соответствующего исхода, допущения и множитель временной зависимости; сохранить происхождение пилотного расчёта. До открытия D закрепить эти параметры, сетку и блоки в неизменяемом плане оценки вместе с основной политикой либо парой. Отсутствие плановых параметров точности не блокирует `preflight` и первое обучение; неизвестные значения не заменять вымышленными. IID-расчёт допустим только как отдельно обозначенная проверка чувствительности.

### 9.5. Выбор и вариант без метаданных

Первый основной результат — оценка одной GCS+Rk. Для последующего сравнения до открытия C_select зарегистрировать конфигурации, затраты, контрольный метод GCS+Rk и правило выбора. После выбора, до открытия D, зафиксировать одну основную пару.

Выбирать только среди вариантов, отвечающих вычислительным ограничениям. Для сравнения исходной модели с одним новым вариантом сравнивать целые суммы Hit_s на общей совокупности с непустыми целями; при равенстве сохранять исходную модель. Время и память публиковать отдельно, без нагрузочных прогонов ради разрешения равенства. При отсутствии целей или неполных результатах победителя не назначать.

Вариант `gcs_rk_metadata370` меняет только M на 370 и квоты описаний/изображений на 80/60. Каталог A_G, B, формулы признаков, порядок и параметры обучения прежние. Признаки B рассчитываются заново; схема с отдельным config_id исключает подмену исходных артефактов. C_select готовится один раз по закреплённому плану. Уже просмотренный D не даёт независимого подтверждения улучшения.

Обязательный вариант `graph_recent_popularity_no_provided_metadata` исключает текстовые, визуальные, поисковые векторы, категорию, цену, их маски и производные признаки, поисковые клики/списки и контекст запроса. Сохраняются ID, события, граф, повторы и статистики A_G; нейросеть и SID выключены.

Каталог, допуск, сессии, единственный запрос, K и M остаются общими. Квоты: 50 на каждое из трёх графовых отношений, 20 повторов, 10 популярности; после удаления дублей список дополняется популярными товарами до 300. Нужны собственные признаки B и ранжировщик.

Критерий B10: произвольная замена предоставленных метаданных не меняет кандидатов, признаки или выдачу этого варианта. На D публикуются V/U/Hit, разность с базовой моделью, интервалы чувствительности и стоимость. Эти результаты сами по себе не дают основания для второго подтверждающего вывода.

### 9.6. Отчёт

Генерировать JSON и Markdown/HTML из одних результатов. Включить все блоки `app:diagnostic-output`: данные, исключения, цепочку охвата, три потери, выдачу, источники, разрезы, стоимость, статусы и основание следующего исследования.

Не заменять отсутствующие данные вымышленными значениями. Для неопределённых отношений, непригодных интервалов и неизмеренных списков сохранять разные причины. В заголовке указывать период, протокол оценки, режим воспроизведения, run_id, хеши планов и пакетов. Полноту телеметрии сохранять как неизвестную. В машинном отчёте `N_obs` — число сохранённых сессий, `N` — число сессий с целью; проверять N≤N_obs≤размера выбранной подвыборки. Основные оценки — `Hit@20` или `DeltaHit@20` в долях.

Критерии завершения: B07–B12, независимый пересчёт на малом примере, совпадение отчёта с исходными сессионными таблицами; после D — проверка `post_D`.

## 10. Сервис, состояние и версии

Сервис поставляется отдельно и не требуется для оценки на D в режиме `ideal_deterministic`. Для портфолио требуется один локальный процесс с профилем `local_checksum_only`. Проверки загрузки модели, входных данных, допустимости рекомендаций, временных границ и повторов сохраняются. PostgreSQL, отказоустойчивость нескольких процессов, RTO/RPO, подпись рабочего пакета и промышленная нагрузка отложены до отдельной задачи.

Основание: `sec:operations-features`, `sec:operations-serving`, `sec:ops-security`, `sec:ops-recovery`.

### 10.1. Адаптеры и API

Для демонстрации достаточно существующих средств хранения в памяти и воспроизведения из файла. Принятие блока и изменение состояния остаются атомарными внутри процесса. Рабочий адаптер СУБД, общая транзакция с журналом и сохранность при аварии узла не входят в текущую задачу.

Предлагаемые маршруты:

| Маршрут | Назначение |
|---|---|
| POST /v1/blocks | Принять один полный блок, вернуть квитанцию/статус и серверное время решения. Принятие событий не означает успешной рекомендации. |
| POST /v1/recommendations | Запросить выдачу по принятому trigger_block_id с ключом идемпотентности. Сервис самостоятельно проверяет допуск первого запроса и Q_max=1. |
| GET /health/live | Проверить работу процесса без изменения пользовательского состояния. |
| GET /health/ready | Проверить готовность пакета, необходимых зависимостей и обязательной записи в установленный срок. |

Разрешён объединённый маршрут блока и рекомендации. В нём a_q фиксируется после атомарного принятия, а общий срок начинается с первого байта. Повтор блока не создаёт новый логический запрос. Повтор рекомендации не продлевает исходный срок.

Публичный ответ содержит query_id, версию пакета, товары, ветвь, статус доставки, безопасный код причины и объяснения по §10.7. Полный список кандидатов, признаки, баллы и сырая история доступны только для диагностики с ограниченным доступом. HTTP-коды не исключают запросы из аналитических знаменателей.

### 10.2. Приём sealed_block_v1

Конверт содержит `source_namespace, session_id, event_time_ms, block_id, event_count, event_ids, events, payload_sha256, closed=true`.

Обязательные проверки:

- отправитель аутентифицирован и зарегистрирован владельцем пространства; один агрегатор объединяет события поведения и поиска;
- все события принадлежат одной сессии и одному времени;
- число событий совпадает с длинами массивов; event_ids[k] равен events[k].event_id; ID внутри блока уникальны;
- сервис сам вычисляет SHA-256 точных неизменяемых байтов данных; границы хешируемых байтов закреплены схемой;
- квитанция связывает пространство, сессию, время, block_id, количество и хеш; одного block_id для признания повтора недостаточно;
- неполный блок не принимается частями; закрытое время не дополняется новыми ID.

| Ограничение | Начальное значение |
|---|---:|
| Конверт / SKU | ≤1 МиБ / ≤256 байт UTF-8 |
| Сырые события конверта | 1–100 |
| Логические события блока / сессии | ≤100 / ≤1000 |
| Поисковый список | ≤1000 элементов |
| Скорость на сессию | 10 сырых событий/с, допустимый всплеск 100 |
| Минимальная стоимость любой попытки | 1 |
| Допустимое запоздание / опережение | 1800 с / 0 с |

Ограничения числа логических событий проверять после удаления повторных ID и канонизации; ограничения скорости — по фактическим сырым событиям, включая повторы. При превышении отклонять новый блок целиком. До распознавания сессии действуют ограничения соединения и отправителя.

Для нового блока проверять −1800 с ≤ t(e)−a_block ≤ 0 с и разрешённый календарный диапазон. Ошибка времени не меняет историю или t_last; будущие события не буферизуются. Подтверждённый повтор проверять до повторной проверки временного окна.

### 10.3. Состояние и переходы

Ключ — (source_namespace, session_id). Запись содержит U_s, номер изменения v_s, версию преобразований, время последнего поступления, полноту и причины разрывов, необходимые агрегаты, общий хвост L_hist=20 блоков, независимую очередь L_H=20 просмотров, последний поисковый контекст и данные расписания.

Сохранять полную последнюю группу просмотров, когда она нужна признакам; общий хвост и очередь L_H не заменяют друг друга. Вытеснение старых блоков не сбрасывает агрегаты всего доступного префикса. Покупки и назначения хранятся независимо от оперативной записи.

| Случай | Действие |
|---|---|
| Новый корректный блок | Одной атомарной операцией записать события, квитанцию, состояние и v_s+1; a(e)=серверное время принятия блока. |
| Конфликт версии | Перечитать и пересчитать переход; не более одного повторного атомарного обновления в пределах исходного срока. |
| Подтверждённый полный повтор | Не менять состояние, полноту, первоначальные времена доступности и ответы. При исчерпании лимита возможен duplicate_rate_rejected без разрыва истории. |
| Прежний block_id с другими данными / новые ID закрытого времени | closed_block_conflict; старую историю сохранить, новую неизвестную часть поместить в карантин. |
| Только известные события | Не создавать новый блок. |
| Смесь старых и новых ID | Не принимать поэлементно; проверить закрытое время и соответствие ID первоначальным полям. |
| Отклонённый новый доверенный блок | Отметить разрыв. Без проверенного префикса — отказ без рекомендаций до восстановления. |
| Непроверяемый повтор | retry_unverifiable; не считать новым событием. Проверка журнала/восстановление определяет полноту. |
| Недоверенный отправитель | Отказать без изменения чужой сессии. |
| Недоступное/несовместимое/неполное состояние | Отказ без рекомендаций, если нет проверенного префикса. Резерв разрешён только при проверенном префиксе и подтверждённой допустимости товаров; пустая история не заменяет неизвестное состояние. |

Запрос получает один подтверждённый срез с t(e)≤t_q и a(e)≤a_q и один совместимый пакет. Если текущая запись содержит более поздние события, восстановить нужный срез. Поздний блок не меняет прошлый ответ.

Восстановление: контрольная точка до хвоста → упорядоченные события хвоста → тот же StateReducer. Ограничения — ≤1000 событий и ≤1 МиБ журнала на запрос, в пределах общего срока ответа. Превышение даёт `state_replay_limit`; фоновая работа не продлевает срок ответа.

Ключ кэша учитывает версию видимого префикса, t_q и пакет, а не только сессию. Закрытый транспортный блок не доказывает полноту сессии: нужен объявленный сигнал полноты потока.

### 10.4. Публикация и откат

Пакет содержит согласованные каталог, граф, векторы, словари, схему признаков, ранжировщик, политику, шаблоны объяснений и включённые расширения. Перед активацией проверять размерности и происхождение пространств, схемы, версии, хеши, зависимости и протокол оценки.

Выбирать последнюю совместимую публикацию строго до t_q, не до a_q. Если её нет — `version_unavailable`; более новый пакет нельзя использовать даже для резерва.

При загрузке запрещены исполнение сериализованного кода, пути вне пакета, неизвестные типы и превышение заявленных размеров. Локальная контрольная сумма допустима только для исследовательского профиля. Рабочий профиль требует подписи Ed25519; доверенный ключ поступает независимо от пакета.

Активация атомарна; запрос закреплён за одной версией. Смена схемы состояния требует проверенной миграции либо восстановления. Откат не меняет старые ответы и не разрешает просроченный каталог.

Для будущего рабочего сервиса: RTO≤60 с и RPO подтверждённых назначений и исходов — 0; испытания восстановления на всех экземплярах. Эти гарантии для демонстрации не требуются. В ней сохраняются отказы при недоступности состояния/каталога, ошибке записи, повреждении пакета и несовместимой схеме; при измерении памяти учитываются одновременно загруженные версии.

### 10.5. Срок ответа и выбор ветви

Использовать монотонные часы для длительностей и абсолютного срока; UTC — для времени событий и публикаций.

Один настраиваемый тайм-аут охватывает весь запрос от первого байта, включая очередь, расчёт, сериализацию, обязательную запись и возврат. Начальное значение для демонстрации — **1000 мс**; его фиксируют до запуска. Это технический предел ожидания, не обещание задержки под нагрузкой. Отдельных нормативных сроков этапов нет: превышение прежних 10/15/25/35 мс само по себе не вызывает отказ.

Основная ветвь прекращает работу с запасом на уже подготовленный резерв, запись и возврат. Запас задаётся параметром исполнения до запуска, не отдельным условием приёмки каждого этапа. Общий срок не продлевается. Сигнал отмены не гарантирует остановки непрерываемой операции; сохраняются ограниченный пул, проверки срока и запрет поздней публикации. Поздний результат не меняет ответ или состояние.

Журнал должен позволять сопоставить запрос, пакет, выбранные кандидаты, публичный ответ и исход. Двухфазная фиксация каждой операции и гарантия RPO=0 для демонстрации не обязательны. Ошибку обязательной записи нельзя объявлять успешным завершением; неизвестную доставку нельзя выдавать за подтверждённую. Повтор возвращает сохранённый исход без пересчёта.

Резерв готовится заранее: последние различные просмотры по убыванию времени, при равенстве ID, затем популярность без повторов. До M=300 кандидатов, до K=20 товаров; тот же фильтр допустимости. Его не объединяют с основной ветвью и не пропускают через основной ранжировщик.

После выбора ветви фиксируются branch и C_served. Если доставка или обязательная запись не уложилась в срок, L пуст, но выбранные кандидаты сохраняются. Если готовая ветвь не выбрана, пусты оба множества. Всегда L⊆C_served⊆I_q. Неизвестная допустимость исключает товар; непригодный резерв означает технический отказ. Ошибка ответа не отменяет принятые события.

Минимальные причины отказа: `invalid_input`, `overload_rejected`, `backend_timeout`, `cancelled`, `state_replay_limit`, `logging_failure`, конфликты блоков, недоступность версии и причины неполноты.

### 10.6. Приёмка демонстрационного API

На готовых пакете и модели проверить четыре сценария: штатную выдачу основной ветви, повтор блока и запроса без пересчёта, вычислительный тайм-аут с доставленным резервом, неполное состояние с отказом без рекомендаций. Тайм-аут должен сработать во время вычислений. HTTP-ответ сверить с прочитанным журналом; поздняя работа не меняет итог.

Измерить полное время ответа с записью, отдельно время загрузки пакета и пиковое потребление памяти. Указать оборудование, число запросов, тайм-аут, ветви и отказы. P95/P99 допустимы как измерения на достаточно большом наборе, но не как обязательные пороги; четыре запроса не доказывают производительность под нагрузкой. Обычное распределение ядер сохраняется, настройка компьютера ради прохождения проверки не требуется.

Приёмка демонстрации — применимые проверки корректности B03.service/B14 и EXPL01 плюс эти четыре сценария. Она не присваивает промышленный `S_serve=passed` или `post_load`. Профиль 100 запросов/с, три длительных прогона, B15/B16 и RTO/RPO из математической спецификации остаются отложенными требованиями рабочего сервиса, а не препятствием для портфолио.

### 10.7. Шаблонные объяснения

Основание: `sec:explanation`. Модуль `explanations` объясняет каждый рекомендованный товар по трассе выбранной ветви и закреплённому пакету. В диагностике сохраняются источники попадания, их баллы и опора объяснения:

| Источник | Расчётная опора |
|---|---|
| Граф | Отношение, товар префикса с наибольшим суммарным вкладом, величина вклада и поддержка n_ij этого отношения; при равенстве — порядок ID. |
| Содержание | Использованная модальность и измеренная близость. |
| Поиск | Ссылка на доступный поисковый запрос, версия совместимого пространства векторов и измеренная близость. |
| Недавние просмотры, популярность, заполнение | Фактическое происхождение товара, без приписывания графовых или содержательных связей. |

Опору получать при расчёте источников либо воспроизводить по закреплённым входным данным; агрегированный балл не заменяет вклад отдельного товара. Резерв объясняется только собственными источниками. Непригодный поиск и неиспользованные источники не становятся причинами рекомендации.

Шаблоны используют только проверенные поля трассы. Внутренняя опора хранится по §11.2; публичная форма — минимальные коды причин без сырой последовательности событий. Она описывает расчёт, а не причину покупки; из обезличенных векторов нельзя выводить название, свойства или совместимость товара. Языковая модель не используется.

Версия и хеш шаблонов входят в пакет. Объяснения формируются внутри общего срока (§10.5). Приёмка — по §15.5.

## 11. Наблюдение, хранение и защита

Эти требования относятся к рабочему сервису и не обязывают создавать инфраструктуру для локального эксперимента. Локально сохраняются ограничения ресурсов, защита закрытых периодов, проверка входных данных и пакета, а сырые данные не публикуются.

### 11.1. Показатели и тревоги

Сразу собирать показатели входящего потока, ошибок, использования резерва, пустых/коротких ответов, неизвестных товаров, пропусков, размера и уникальности списка кандидатов, версии/возраста пакета, задержек и памяти. Для расширений — также маски, нормы, усечения, согласие индекса с точным поиском и коллизии.

Для сдвига распределений:

- границы числовых групп и категории фиксируются на ранних данных; пропуск — отдельная категория, сглаживание гистограмм ε_h=1/2;
- базовое окно — ≥10 000 запросов; текущие непересекающиеся часовые окна UTC — ≥1000 запросов и ≥200 сессий;
- для настройки порога нужны ≥100 контрольных часовых окон до C_select, отдельно от базового окна, с доступной к каждому окну базой;
- A_w=max_j(JS_wj/0,05), h=max(1, квантиль 0,99 по nearest-rank);
- тревога — два последовательных достаточных окна A_w>h; снятие — три окна A_w<0,8h; повторное уведомление причины — не чаще раза в час;
- недостаточное окно не считается стабильным; три подряд дают отдельное уведомление. Оценивать частоту срабатывания всего правила, а не только превышений в отдельных окнах.

Тревога запускает диагностику полноты, версий и источников, не автоматическую замену модели.

Операционная защита:

- два соседних пятиминутных окна с ≥1000 запросов и превышением 0,1% ошибок либо 1% резерва включают проверенный резерв/откат;
- независимо от объёма: 20 последовательных технических отказов корректных допущенных запросов либо три неуспешные внутренние проверки;
- внутренние проверки — каждые 5 с со сроком 120 мс, отдельными ID и без пользовательских изменений;
- последовательность определяется порядком поступления, зависший запрос получает исход по сроку, успех сбрасывает соответствующий счётчик;
- недоверенный ввод и отдельная попытка загрузить неподлинный пакет не откатывают исправную версию; недопустимая выдача блокируется немедленно.

В исторической оценке Hit@20 считается по зарегистрированным целям; отсутствие покупки в выгрузке не становится нулевой конверсией. Исходы покупок в рабочем A/B анализируются после завершения окна наблюдения и проверки его полноты. Во время подтверждающего A/B модель и поведенческие справочники зафиксированы, если иной режим заранее не обоснован протоколом.

### 11.2. Доступ и сроки

| Сущность | Начальный срок |
|---|---|
| Оперативное состояние | 24 часа неактивности |
| Проверяемость повторов | Не менее 24 часов независимо от TTL состояния |
| Журнал воспроизведения | 48 часов |
| Подробные трассы | 7 суток |
| Минимальные назначения и исходы | До закрытия анализа +30 суток |

Назначить владельцев хранилищ; реализовать разграничение ролей, шифрование передачи и хранения, аудит чтения трасс. Обычный журнал содержит псевдонимный ключ, версии, ветвь, товары и статус, но не сырые запросы, векторы и всю историю.

Простое хеширование ID не считать анонимизацией. Преобразование идентификаторов использует секретный ключ и разделяет пространства. Ключ назначения стабилен на горизонте эксперимента; смена диагностических ключей его не меняет.

Удаление охватывает состояние, журналы, диагностику и резервные копии. После восстановления повторно применять реестр удалений. После истечения срока хранения входных данных точное воспроизведение невозможно; агрегированные результаты без сессионных ключей могут сохраняться. Указанные сроки — настройки проекта, а не правовое заключение.

Критерии завершения: B15/B16, тесты удаления и восстановления удалённых ключей, отсутствие сырых данных в публичных ответах и обычных журналах, указанные владельцы и параметры рабочего профиля.

## 13. Подготовка и анализ A/B

Пилот в рабочем сервисе проводится после отдельного допуска и не входит в локальную оценку Coveo. Нормативные условия — `sec:eval-online`, `sec:eval-itt`, `sec:eval-srm-stop` математической спецификации; приёмка — B18 и pre_AB/post_AB.

### 13.1. Назначение и журналы

До первого показа зафиксировать протокол, единицу назначения, когорту, вариант, сроки, объём и защитные правила. Обеспечить устойчивое назначение, полноту журналов и учёт всех назначенных сессий по нормативному протоколу. Проверки B18 выполнить до pre_AB, включая независимые искусственные примеры.

### 13.2. Контроль и анализ

ITT, SRM, интервалы, правила остановки и зрелость исходов — по указанным разделам спецификации, без подбора после просмотра результатов. Отсутствие эксперимента означает `not_observed`, а не нулевой или положительный эффект. По таблицам Coveo не реализовывать IPS/DR с вымышленными вероятностями показов.

## 14. Команды и поведение конвейера

Единый интерфейс — `coveo-recsys`. Названия подкоманд проектные; реализованный набор указан в README.

| Команда локального маршрута | Назначение |
|---|---|
| manifest init / validate | Создать и проверить паспорт запуска по §4. |
| data inspect / prepare | Проверить и подготовить данные по §5. |
| historical build | Построить пакет A_G по §6. |
| features build --period B / train ranker | Рассчитать признаки и обучить модель по §§7–8. |
| replay --period C_smoke | Получить диагностическую выдачу и отчёт по §9. |
| sensitivity metadata | Построить обязательный к D вариант без метаданных по §9.5. |
| selection freeze / run | Зафиксировать план и выполнить выбор на C_select. |
| evaluation freeze / run --period D | Проверить pre_D, зафиксировать план и выполнить итоговую оценку. |
| report --run ... | Собрать отчёт из сохранённых результатов без нового выбора или обучения. |

Проверки выполняются стандартным запуском `pytest`; отдельная команда регистрации и система хранения паспортов тестов не требуются. Команды сервиса, нагрузки, восстановления, расширений, A/B и удаления данных добавляются на соответствующих этапах (§§10–13).

Первый проход: паспорт → проверка и подготовка данных → пакет A_G → preflight → признаки B → обучение → post_training → C_smoke. Подготовка и сборка A_G проверяют свои входные данные и результаты, но не присваивают `preflight=passed`. Полный допуск нужен до расчёта признаков B и обучения. Проверка чувствительности без метаданных, сервис и A/B не блокируют этот проход; обязательные сроки их проверок — в §15.2.

Долгие команды сообщают ход выполнения, объём данных, пик памяти и причину ошибки. Возобновление допускается только с совместимых результатов, без смены выборки и порядка случайных вызовов.

Техническая ошибка возвращает ненулевой код. Непройденное обязательное условие запрещает расчёт; статус `insufficient` не подменяется успехом. Локальные команды проверяют разрешённые периоды и записывают факт их открытия; обучение и выбор не читают закрытые оценочные данные. Рабочий сервис дополнительно применяет правила доступа §11.2.

## 15. Тестирование и прослеживаемость

### 15.1. Общий порядок

Проверки выполняются через `pytest`. Для каждого ID требования указать тесты и этап, на котором они обязательны (§§15.2–15.3); входные данные, независимый эталон, допуски и начальное состояние генератора хранить с тестами. В результате запуска сохранить версию кода, конфигурацию, выполненные проверки, статусы и причины отказов или пропуска. Отдельная предварительная регистрация и паспорт с хешем для каждого теста не требуются.

Для локальных `preflight` и `post_training` на Windows допускается узкое платформенное исключение: явно перечисленные тесты символических ссылок могут быть пропущены только из-за отсутствия права их создавать (`WinError 1314`). В JUnit и сводке они остаются `skipped`, не включаются в число успешных и отмечаются как ограничение запуска. На Ubuntu эти тесты обязательны. Любой другой пропуск или неуспешная применимая проверка блокирует допуск; защита путей и сами тесты сохраняются.

Эталон должен быть проще основной реализации и не вызывать проверяемую функцию для получения ожидаемого результата.

Для каждого свойства, проверяемого на сгенерированных данных, — минимум 1000 случаев, начальное состояние 17; сохранять версию генератора и минимальный контрпример. Дополнительно выполнять обязательные малые примеры спецификации.

Множества, маски, счётчики, категории, версии и порядок — точное равенство. Для чисел использовать объявленные допуски:

| Проверка | Допуск |
|---|---|
| Общие FP64-вычисления | atol=10⁻¹⁰, rtol=10⁻⁸ |
| Общие FP32-вычисления | atol=10⁻⁶, rtol=10⁻⁵ |
| Производные до приведения | atol=10⁻¹², rtol=10⁻¹⁰ |
| Производные после FP32 | atol=10⁻⁷, rtol=10⁻⁶ |
| Конечные разности парной потери, шаг 10⁻⁴ | абсолютная ошибка градиента≤10⁻⁷, гессиана≤10⁻⁶ |
| Соответствие признаков воспроизведения и сервиса | Формула из раздела 7.2, а не замена её общим допуском |

Неожиданный NaN/Inf — отказ. Смысл разрешённых исключений, например +∞ для задержки отказа, задаётся отдельно. Почти равные баллы не позволяют игнорировать изменение порядка товаров.

B03.data/B03.service — части одного постоянного ID B03, а не новые нормативные тесты. Аналогично X02.support/X02.loss. Фактические результаты D и A/B записываются только на post_D/post_AB. Ранние B10–B12 выполняются на независимых малых примерах; реальные C_select и D остаются закрытыми до допуска, E не используется.

B05 выполнять частями: векторную и численную — к Э3, производные и проверки LightGBM — к Э4.

B10.data выполняется на preflight, B10.ranker — к первому применению модели; B10.metadata — до использования варианта без метаданных. B11 подтверждает отключение компонентов, а не качество калибровки. Перед D проверяются применимые B10–B12 и фактические входные данные; настройки B11 проверяются паспортом, без отдельного этапа E. Малые примеры проверяют реализацию, а не результаты на закрытых данных.

Части B05 и B10 можно отражать в общем результате тестового запуска. `passed` требует всех частей, применимых к текущему расчёту. Невыполненные поздние части остаются явно отмеченными, а не считаются пройденными.

B18 не блокирует локальные обучение и оценку. До A/B обязательны и независимые примеры, и проверка реального протокола. Различие исторического охвата и причинного эффекта сохраняется во всех отчётах.

### 15.4. Сквозные испытания и автоматизация

Обязательный малый набор содержит: одновременные покупки/просмотры, несколько будущих покупок, повтор SKU, пустую цель, пропуски поиска и векторов, неоднозначный поиск, дубли, пустую историю, корзину с конфликтом, неизвестный SKU, короткий каталог, запрос без положительного кандидата, календарное исключение, пропуск опубликованной строки и каждую точку перехода на резерв. В B06 воспроизвести нормативный пример: 3 сохранённые сессии, 2 с целью, 1 попадание дают Hit@20=1/2, а не 1/3.

На нём проверить полный маршрут: исходные строки → канонизация → запросы/цели → A_G → кандидаты/признаки B → обучение → воспроизведение → метрики → паспорт. Результаты сверить с независимыми ручными/прямыми расчётами.

Автоматическая проверка изменений включает проверку схем, статический контроль типов, быстрые тесты, эталоны и применимые проверки свойств на сгенерированных данных. Длительные прогоны обучения, нагрузки и анализа A/B запускать отдельными заданиями с сохранённой конфигурацией. Пропуск из-за отсутствия ресурсов или данных не считается пройденным тестом.

### 15.5. Проверка объяснений

EXPL01 — дополнительный тест ТЗ, не заменяющий 30 нормативных ID. Связь требований: `sec:explanation` → `explanations` и структура Explanation (§10.7) → Э6 / `post_load` → EXPL01. Входные данные, независимые эталоны и результаты — по §15.1.

Проверить максимальный графовый вклад и поддержку ребра, равенство вкладов, модальность и близость, непригодный поиск, несколько происхождений, заполнение и резерв. Объяснение должно соответствовать товару, выбранной ветви, версии пакета и шаблона. Публичную форму проверить на отсутствие причин от неиспользованных источников, сырой истории и неподтверждённых свойств товара.

## 17. Состав поставки и окончательная приёмка

### 17.1. Поставляемые результаты

Для локальной версии:

- Код, закреплённые зависимости и инструкция воспроизведения.
- Проверенные входные данные, паспорт запуска, планы и результаты выполненных этапов по §§3–4.
- Исторический пакет, схема признаков, ранжировщик; вариант без метаданных — к оценке на D.
- Искусственные наборы, независимые эталоны, соответствие ID требований тестам и результаты их выполнения.
- Отчёт C_smoke; после допуска — результаты выбора и D по §9.
- Описание ограничений, недостатка данных и ещё не реализованных возможностей.

Для портфолио поставляются API, объяснения, команда запуска, результаты четырёх сценариев и измеренные задержки по §10.6. Промышленная нагрузка, восстановление и эксплуатация по §11, расширения и A/B выполняются только по отдельной задаче.

### 17.2. Раздельные решения

Приёмка кода подтверждает реализацию заявленных модулей, команд и граничных ветвей, а также соблюдение проверяемых свойств. Она не подтверждает пригодности конкретных данных, статистической точности или пользы модели.

Итоговый статус системы хранить раздельно: S_data, S_math, S_offline, S_serve, S_business. Для бизнес-эффекта без эксперимента — `not_observed`. Пока D закрыт, S_offline=`not_run`; `calibration_status="not_used"` во всех стадиях текущего протокола.

- Нарушение контракта или превышение технического порога — `failed`.
- Корректная процедура при нехватке сессий с зарегистрированной целью, блоков или точности — `insufficient`.
- Если одновременно есть нарушение и недостаточность, `failed` имеет приоритет; сохраняются все причины.
- S_offline=`passed` означает пригодность оценки, а не превосходство модели.
- Неизвестная полнота телеметрии не блокирует условную историческую оценку, но не разрешает оценивать конверсию всех сессий или бизнес-эффект.
- Готовность к пилоту требует S_data=S_math=S_offline=S_serve=`passed` именно в рабочем профиле: подпись, лимиты, доступ/хранение и проверенная настройка порогов мониторинга. Для A/B дополнительно требуется наблюдаемость исходов по §13.
- Успех локального `local_checksum_only` не разрешает рабочий пилот. Преимущество по бизнес-показателям требует отдельного успешно пройденного причинного анализа.

Успех команды, отчёт или хеш не заменяют обязательных условий приёмки. Отрицательные и недостаточные результаты сохранять с фактическим статусом; при недостатке информации нельзя обещать `passed`.
